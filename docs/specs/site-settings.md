# Site settings page

> The admin address is `config('hata.admin.path')` (env `HATA_ADMIN_PATH`, default `admin`); `/admin` in this spec stands for it. Route names stay `admin.*`.

Settings for the whole site that an administrator changes in the admin panel instead of editing `.env` (shared hosting often has no SSH). The page is a list of registered sections (decision 75); a site or module adds its own (see [package](package.md#adding-a-settings-section)).

## Page

| Page | Route | Name | Permission |
|---|---|---|---|
| Site settings | `/admin/settings` | `admin.settings.edit` | at least one section the user may open |

The page is the Livewire SFC `resources/views/livewire/admin/settings/edit.blade.php`: a shell that holds the list of sections, the open one and the leave-page guard, and renders the open section as a component of its own (`<livewire:dynamic-component>`). The route has no `can:` middleware: the shell answers 403 when the user may open no section. The navigation item "Site settings" (Administration group) is shown when the user may open at least one section, decided from permissions alone (`SettingsSections::visibleTo()`), with no query and no component resolved. Hata's seven sections all need `settings.edit`, which the `admin` system role gets through `*`.

## Sections

The registry is `Hata\Support\Admin\SettingsSections` (a singleton; sections are `SettingsSection` value objects: key, label, icon, Livewire component, permission, order). Hata registers its own in `HataServiceProvider::registerSettingsSections()`:

| Key | Label | Order | Component (`hata::admin.settings.sections.…`) | What it holds |
|---|---|---|---|---|
| `site` | Site | 10 | `site` | site name, timezone |
| `languages` | Languages | 20 | `languages` | the site's content languages (applied at once), the default interface language |
| `content` | Content types | 30 | `content` | switches for the registered content types (applied at once, no Save) |
| `access` | Access | 40 | `access` | public registration, role of new users |
| `mail` | Email | 50 | `mail` | sending method, SMTP, sender, test email |
| `appearance` | Appearance | 60 | `appearance` | the light and dark logo, the color scheme |
| `media` | Media | 70 | `media` | optimization, limits, storage (this server or S3) |

Sections are listed by order (ties keep the order they were added in), at the side (`flux:navlist`, sticky) from a tablet up and as a row that scrolls (`flux:navbar`) on a phone; Flux free has no tabs component. The open section is in the query string (`?tab=<key>`; kept under the name `tab` so old links work). An unknown key, or one the user may not open, opens the user's first section. These keys of the earlier tabs are aliases: `general` opens `site`, `logo` and `colors` open `appearance` (`SettingsSections::ALIASES`; a section that registers one of those keys itself wins over the alias).

**Access is per section.** A section's permission is a gate ability, a closure `fn (AdminUser $user): bool`, or null for any admin. A user sees only the sections they may open, and the menu item and the page need at least one. Every request to a section re-checks its permission (`SettingsSectionPage::hydrate()`, on top of `mount()`, `save()` and the section's own actions), because a Livewire request can name any component; a section that is not registered is refused too.

**Registration mistakes** (a key that is not lowercase words joined by hyphens, a component Livewire cannot resolve) follow the admin menu: a `LogicException` naming the section in `local` and `testing`, elsewhere the section is left out and a warning is logged once per process. The sidebar decides from permissions only, so in production a broken module section can leave an item that opens a page without it (or a 403 when it was the user's only one).

**Switching sections is navigation** (`wire:navigate` to `?tab=`), so one browser guard covers switching and leaving the page. The shell asks the open section's Alpine `isDirty()` (a field differs from the copy the section loaded, or a secret field has been typed; it reads `$wire.values` and `$wire.saved`, so it also sees edits not yet sent to the server). A `wire:navigate` link (the section list, the sidebar) is cancelled through the `livewire:navigate` event and a confirmation "Leave without saving" opens; closing or reloading the tab and plain links get the browser's own `beforeunload` dialog. **The browser's Back and Forward buttons are not guarded**: `livewire:navigate` with `history: true` arrives after the URL has already changed. Since each section is a URL, switching sections now adds history entries, so Back moves between sections, and an unsaved change is dropped without a warning when Back is used. A successful save marks the form clean before its redirect.

**Saving.** Each section has its own "Save" button, which validates and stores that section's fields and redirects back to it with a success toast (a full reload, so the layout shows the new site name or colors). Save stores only the fields the admin changed from the values loaded when the section opened (`SettingsSectionPage::changed()`), so a value that comes from `.env` or a config default and was left alone is never frozen into the database (decision 36), and a save that changes nothing writes nothing. A secret field (the SMTP password, the S3 secret) starts empty, is never loaded or rendered, and is stored whenever something is typed; a blank value never removes a stored secret. A section's component declares `fields()` and `rules()`; only fields with a validated `values.<field>` rule are stored, and a field without one is reported (`LogicException` in `local` and `testing`, a logged warning elsewhere) and never saved. Settings written by something other than the form (the logo's usage, the direct-serving probe) go through the actions listed below.

## Storage

- Table `settings` (`key` unique, `value` JSON), model `Hata\Models\Setting`.
- `Hata\Support\Settings\SiteSettings` (singleton) reads all rows through the cache (`site_settings`, forever) and writes each one over its config value in `HataServiceProvider::boot()`. The rest of the code keeps reading `config()`. A queue worker boots once, so `Queue::before` (also in `HataServiceProvider`) applies them again before every job except on the `sync` connection (those run inside a request that already applied them, and re-applying would undo `SetLocale`'s `app.locale`), and `media:optimize`/`media:move-disk` before every batch (decision 48); `apply()` first restores the config values of settings applied earlier, so a setting removed meanwhile falls back to `.env` there too. The resolved `s3` disk is forgotten (`Storage::forgetDisk('s3')`) only when `apply()` changed its config, so a worker or command that applies the settings before every batch keeps its client.
- **The keys are a registry**, not constants: `SiteSettings::define($key, ?$config, ?$cast, $encrypted)` declares a key with the config path it overrides (null for a stored-only value the app reads itself), its cast (`int`, `bool`, `array`, applied when the value reaches config) and whether it is stored encrypted with `APP_KEY` (a row that cannot be decrypted is ignored). Hata defines its own keys in `HataServiceProvider::defineSettings()`; a key defined after the settings were applied is applied at once. `definition($key)` and `isDefined($key)` read it back. An undefined key is never applied, and `put()` reports it (a `LogicException` in `local` and `testing`, a logged warning elsewhere) and does not store it.
- A setting that isn't stored leaves the config value (from `.env`) in place. `put()` with `null` deletes the row and restores that value. Once saved, stored values win over `.env`.
- While the table doesn't exist yet (fresh install before `migrate`), no settings are applied.
- `put()` forgets the cache, re-applies the settings and drops resolved mailers, so a change works in the same request.

## Fields

- **Site name:** required, ≤255.
- **Content types section** (`content`): every registered content type with its icon, name, description, record count (one grouped query, the trash included) and a switch. Switching a type on applies at once; switching one off asks first (`<x-hata::confirm-modal>`: its pages leave the site, nothing is deleted). Each change is `Hata\Actions\Settings\SetContentTypeActive` (`settings.edit`), stored as the site setting `content_disabled_types` (config `hata.content.disabled_types`), followed by a reload of the section so the sidebar shows the change. A type whose `required()` is true (pages) has no switch and the mark "Always on". The section has no Save button (`<x-hata::admin.settings-section :save="false">`). See [content](content.md).
- **Languages section:** the site's content languages (added from the catalogue, switched on and off, the default; each change is stored at once, see [languages](languages.md)) and, saved with the Save button, **Default interface language**: one of `hata.admin.interface_locales`, for guests and users without a language. The field shows the site's value, not the administrator's own language.
- **Timezone:** any PHP timezone. Dates are stored in UTC (`app.timezone` doesn't change); admin views convert with `->tz(config('hata.admin.timezone'))`.
- **Public registration:** switch. Fortify always registers the registration routes; `Hata\Http\Middleware\EnsureRegistrationIsEnabled` (in `fortify.middleware`) answers 404 while it's off, and the "Sign up" links check the setting.
- **Role of new users:** "No role" or any role except super-admin. Roles the actor can't assign (rule 5, `RolePolicy::assign`) are disabled. A warning is shown when the role has `admin.access`. `CreateNewUser` gives the role and never gives super-admin.
- **Email:** sender address (required, email) and name (required). Sending method "Server settings (.env)" or "SMTP server". With SMTP: host and port (1–65535) required, encryption STARTTLS (`smtp`) or SSL/TLS (`smtps`), username, password. The password is stored encrypted with `APP_KEY` (a row that can't be decrypted is ignored), is never sent to the browser, and an empty field keeps the stored one. Choosing the server method deletes every SMTP setting.
  - Layout (2026-11-12): the SMTP fields sit in a bordered block: server, port and encryption on one row (3/1/2 of six columns; the span is on a wrapper `<div>`, because a class on a Flux field with a label goes to the input, not the grid cell), login and password below. "Send a test email" is its own block under the Save button, with its hint next to the button.
- **Send a test email** (Email section only): to the current user's address with the saved settings (not the unsaved form). A transport error is shown in a danger toast.
- After saving: a full redirect back to the same section (so the layout shows the new site name) with a success toast.
- **Mail fields are stored together.** Choosing the SMTP method stores the whole connection (host, port, encryption, username), not only the fields that differ from the form's blank start, so it never half-follows `.env`.

## Appearance: logo

- **Default mark:** `<x-hata::app-logo-icon>`, a house with crossed rafters over the gable and a four-pane window (`currentColor`). `favicon.svg` (follows the system theme), `favicon.ico` and `apple-touch-icon.png` (in `resources/static`, built into `dist/` and served from `/vendor/hata/`) use the same mark. Chosen logos don't change the favicon.
- **`<x-hata::site-logo class="h-8">`** shows the chosen logos (light one with `dark:hidden`, dark one with `hidden dark:block`) or the default mark on an accent tile. Used by `<x-hata::app-logo>` (sidebar, header) and the auth layouts; `variant="dark"` always shows the dark one (the dark panel of the split auth layout).
- **Logo slots:** a light and a dark slot, each with a preview on a matching background and the media picker (`accept` image, single, extensions PNG, JPG, JPEG, WebP, SVG; GIF and documents are refused). Choosing a file or the picker's own "Remove" only changes the form (`values.logo_light`, `values.logo_dark`: the media id, null without a logo); nothing is stored until the Appearance section's Save, which supersedes the earlier "stored as soon as it is chosen". Logos and colors are saved **together, all or nothing**: Save runs `SetLogo`/`RemoveLogo` and `UpdateSiteSettings` for the changed fields in one transaction, so a refused logo (a field error on the slot) rolls the colors back too, and the settings cache and config refresh only after commit. Removing stops using the logo, the file stays in the library. Without `media.view` the picker hides itself and shows its own "needs access to the media library" hint (one per slot); the current choice stays visible.
- **Fallback:** with only one logo chosen, it's used in both themes (`SiteLogo::media()`). A missing row, a file missing on disk or a file that isn't a logo format counts as empty; with both empty the default mark is shown (never an `<img>` with a dead URL). In Appearance such a dangling slot (the setting holds an id but `SiteLogo::own()` returns null) shows "The logo file is missing." with a "Remove" button (`removeLogo`), since the picker has no choice to remove. That button is the one logo action that stays immediate: it removes the logo at once, without Save, and reloads the section with a toast. Lookups are memoized per request and forgotten whenever the settings are applied (`SiteLogo::flush()`).
- **Cost per page:** both variants are looked up with one query per request (`SiteLogo::load()`), then remembered for the request.
- **Storage:** the setting holds the media id. `SetLogo` (`settings.edit`; also `media.view` unless the id is already the stored one, so a user without library access can't take arbitrary files) validates it with `MediaSelection(accept: 'image', extensions: SiteLogo::EXTENSIONS)`, stores it through `SiteSettings::put()` and records the usage (`MediaUsage::sync($settingRow, 'logo_light'|'logo_dark', [$id])`). `RemoveLogo` removes the setting and its usage row; the file stays.
- **Usage and deleting:** `Setting` implements `UsesMedia`: the label is "Site logo (light)" / "Site logo (dark)", the link goes to the Appearance section for viewers with `settings.edit`. Deleting the file in the library (also through a folder) calls `Setting::forgetMedia()` inside the delete transaction, which removes the setting; `SiteSettings::put()` clears the cache and re-applies the config only after commit (`DB::afterCommit`), so a delete that fails leaves the logo and files as they were.
- **Serving:** logos are ordinary media files served by `MediaController` (`/media/{key}/{name}`, see the media spec); there is no `branding.logo` route.

## Appearance: colors

- **Scope:** the admin panel and the sign-in pages (every layout that includes `partials/head`). Public themes come later.
- **Presets** (`ColorScheme::PRESETS`, key → company color + base gray): neutral (stock look, no overrides), blue, indigo, violet, rose, orange, amber, emerald, teal.
- **Custom** (one per site): company color (`#rrggbb`, color picker + text field) and base gray (neutral, zinc, slate, stone, gray). The company color is kept when a preset is chosen, so switching back restores it.
- **Tint the sidebar** (on by default, hidden for neutral): light shade (step 50, border 100) in the light theme, deep shade (950, border 900) in the dark theme; off uses the base gray.
- **How it works:** `Hata\Support\ColorScheme\ColorScheme` builds an 11-step accent scale from the company color in OKLCH (`Oklch`, fixed lightness per step, chroma scaled, clipped to sRGB) and writes CSS variables in `partials/color-scheme` (an inline `<style id="color-scheme">` after the Vite CSS): `--color-zinc-*` (base gray; Flux uses zinc everywhere), `--color-accent`, `--color-accent-content`, `--color-accent-foreground`, `--color-sidebar`, `--color-sidebar-border`, for `:root` and `.dark`. No CSS rebuild. `resources/css/app.css` defines the sidebar variables for the stock look; the layouts use `bg-sidebar` / `border-sidebar-border`.
- **Rules:** light accent = the company color; light accent text = the first of it or steps 600–900 with 4.5:1 on white. Dark accent = the company color if it is already light (OKLCH L ≥ step 500), otherwise step 500; dark accent text = the first readable (4.5:1) on gray 800. Text on accent buttons = white while contrast ≥ 3:1 (WCAG for UI), otherwise step 950.
- **Role badges** in the user list use the accent (`bg-accent/10`, `text-accent-content`); super-admin stays amber.
- **Preview:** the Appearance section renders the form's scheme in an inline `<style>` (including the stock values, so "Neutral" previews over a saved scheme). Saved with the section's Save button (together with the logos), guarded by the unsaved-changes warnings like the other sections.
- **Custom stores its parts:** choosing the custom scheme stores its company color and gray with it, so the scheme never half-follows the config.

## Media

Details of the settings and their defaults are in [the media spec](media.md#site-settings--media-section-screen-7).

- **Types in config:** the `int` and `bool` casts of the key definitions (`SiteSettings::define()`) make int settings ints and boolean settings real bools when they are applied to config (`OptimizeImage` checks `is_int(max_side)`). "Do not scale" is stored as `0` (a `null` would delete the row and bring back the default 2560) and applied as `null`.
- **Fields:** switches for the booleans, a native select for the longest side (1920, 2560, 3840, none), a range input for quality (50-100) with its value shown, radios for the format. The optimization options are hidden while "Optimize images" is off.
- **Format:** only `webp` and `original` can be saved. AVIF is listed disabled in Part 1: "not supported by the server" when the driver can't encode it (`ServerCapabilities::supportsAvif()`, a 1x1 test encode cached for a day under `media.avif_supported`), otherwise "not available yet".
- **Limits:** 1-512 MB each. The section shows the server cap, `min(upload_max_filesize, post_max_size)` from `ServerCapabilities::uploadCapBytes()` (bound in the container, tests replace it). A limit above the cap is a field error (`media.errors.limit_above_server`), checked only when the value differs from the one in effect, so the untouched defaults (30/20 MB) never block saving on a server with a low cap (e.g. PHP's default 2 MB); the cap line stays as the warning. No cap is shown when PHP sets none.
- **Optimize existing card:** shown below the optimization options for users with `media.edit`: the number of stored images that don't match the saved settings (`Media::optimizationCandidates()` with `OptimizeImage::fingerprint()`, not the unsaved form) and the estimated saving (85% of the size of never-optimized files plus 20% of the rest, two SQL sums), or the progress of a running or paused run ("Paused: N of M files"; a stale run is ignored), or, while optimization is stored as off (the saved setting, not the form switch), only a "save to see" hint with no counts or button, or "All images match the current settings"; the button opens `admin.media.optimize`. The queries run only in the Media section.
- **Storage** (Media section, below the limits): "Where new files are stored" (This server = the `public` disk / S3-compatible storage; the form field `media_storage` takes `public` or `s3`, loads as `public` unless the disk is `s3`), then endpoint (empty = AWS), region, bucket, path prefix, access key, secret key, "path-style endpoint" and public/CDN URL. The connection fields are shown only while `s3` is selected or rows are on `s3`. Values in effect (stored over `.env`, `AWS_*` incl. `AWS_ROOT`) fill the form. `SiteSettings::apply()` writes them over `hata.media.disk` and `filesystems.disks.s3.*` and, only when that changed the disk's config, forgets the resolved disk (`Storage::forgetDisk('s3')`, see Storage above), so a changed setting is used by the next request and by queue jobs at once. A connection field left blank is not stored, so it falls back to its `.env` value (`AWS_*`); a blank field can't clear an `.env` value, only override it with another one. The package `league/flysystem-aws-s3-v3` provides the adapter. The prefix is the disk's `root` (slashes around it dropped); the public URL is stored without a trailing slash.
- **Secret key:** stored encrypted with `APP_KEY` (an `encrypted` key definition), never loaded into the form or rendered; an empty field keeps the stored one (the field says so when one is saved; when the key comes from `.env` only, it says the server configuration's key is used). It is required only when s3 is chosen and none is in effect.
- **Direct serving status:** under the radio, only while the *saved* storage publishes files (`MediaDisks::publishes(config('hata.media.disk'))`, not merely selected in the unsaved form), a status line for `DirectServing::state()` (`site_settings.media.storage.direct.{direct,unchecked,link_missing,unreachable}`; `unreachable` names the probe URL) with at most one button. `link_missing` shows "Create the storage link" (`createStorageLink()` checks `settings.edit` (403 otherwise), runs `CreateStorageLink`, toasts `link_created` or the exception's message, and on success runs `window.checkMediaDirect?.(true)`). `unchecked` and `unreachable` show "Check again" (`window.checkMediaDirect?.(true)`: a forced probe whose result is always recorded); `direct` shows none. The status block listens for the `media-direct-checked` window event, which the probe script fires once the server recorded a result (forced or automatic), and refreshes itself (`$wire.$refresh()`), so it is never left stale after the automatic probe. The probe config (`window.mediaDirectProbe`) is rendered on this page even when no check is due (`partials/media-direct-probe` forces it on `admin.settings.edit`, `auto` false unless a check is due).
- **Test connection** (`TestStorageConnection`, button in the section): builds a throwaway disk with `Storage::build()` from the form's values (the unsaved ones; an empty secret falls back to the one in effect), writes, reads back, lists and deletes `hata-connection-test-{ulid}.txt`, and returns `['ok' => true]` or the failing step (`credentials`, `bucket`, `region`, `endpoint`, `write`, `read`, `list`, `delete`) with a translated message; credential, bucket and endpoint problems are recognised from the AWS error (keys: `InvalidAccessKeyId`, `SignatureDoesNotMatch`, ...; region: `AuthorizationHeaderMalformed`, `PermanentRedirect`, `IllegalLocationConstraintException`; bucket: `NoSuchBucket`, `InvalidBucketName`; endpoint: no response at all). A blank bucket, region, key or secret fails before any request. After a successful write the object is always deleted again (best effort; a failing cleanup never hides the real failure). The button is limited to 10 tests a minute per user. The AWS error is recognised wherever it sits in the exception chain. Timeouts are 5 s to connect and 15 s total. The secret is never logged or returned. The disk comes from the protected `disk()` method, the seam tests override so they never reach the network. The result shows in a callout and disappears when a connection field changes.
- **Saving the section:** a storage field (storage, endpoint, region, bucket, key, secret, path style, public URL, prefix) is stored only when the admin changed it from the value loaded when the section opened (the same rule as every field, see Sections, but kept here because `.env` is the usual source of these values); untouched ones stay unstored so `.env` keeps working (decision 36), and a save that changes none (e.g. image quality) writes no `media_s3_*` rows and never touches the network. When a connection field changed or the storage is switched to `s3`, and storage is `s3` or any row is on `s3`, the same test runs first with the values in effect plus the changes, and the save is refused with "The storage was not changed. {reason}" on the storage field; with `public` chosen and no row on `s3` the fields are saved without a test. Bucket, access key (and region, secret as needed) are required for `s3`. While any media row is on `s3`, clearing the bucket or key is refused with a field error ("move them first"). Changing the bucket, endpoint, prefix or public URL while rows are on `s3` first asks for confirmation (existing files must already be at the new location); "Save anyway" saves. Switching back to `public` is allowed and never runs the test, even with a broken connection. **The private `MEDIA_DISK=local` mode:** the form loads `media_storage` as `public` whenever the disk is not `s3`; while the private mode is in effect `MediaSection::changed()` adds `media_storage` to the changed fields, so Save stores `public` and ends the mode (decision 52), without running the connection test. With the disk already `public` an untouched choice is never stored.
- **Other disk:** when some files are not where the saved storage would put them, a callout says how many ("N files are not stored where new files go") and, for users with `media.edit` (`MediaPolicy::moveToDisk`), links to the move page (`admin.media.move`, "Move them to {storage}"; see media.md → Move files between disks). The count is `MoveMediaToDisk::candidates((string) config('hata.media.disk'))->count()`, the same rule the move page uses, so private PDFs and SVGs that belong on `local` with storage `public` are never counted. It runs once per page load, when the Media section first renders, and is kept in a locked component property (`filesOnOtherDiskCount`), so updates of the section never repeat it. While the configured storage is not a move target (the private `MEDIA_DISK=local` mode from `.env`) the count is 0 and the callout and link are not shown.
- **Helpers:** `Hata\Support\Media\MediaDisks::isCloud($disk)` (the disk's configured driver is anything but `local`; an unknown disk is not cloud), `::publicUrl($disk)` (configured `url` without a trailing slash, or null), `::publishes($disk)` (the disk named `public` with a local driver, decided by identity and not by its URL, so placement keeps SVG, documents and originals off it even when its URL is blank; building a static URL additionally needs the URL, checked in `DirectServing::active()` and before rendering the probe), `::versionsPaths($disk)` (cloud or publishing: versioned paths, deferred deletion), `::originalsDisk($disk)` and `::diskFor($siteDisk, $kind, $mime)` (placement).

## Action (`src/Actions/Settings`)

| Action | Permission | Rules |
|---|---|---|
| `SetLogo` | `settings.edit` | stores a library file's id as the logo and records the usage; called by Appearance's Save inside its transaction (`assign()` does it without checks, for callers that already validated the id) |
| `RemoveLogo` | `settings.edit` | removes the setting and its usage; the file stays |
| `UpdateSiteSettings` | `settings.edit` | stores only the keys it's given (the changed fields of one section); owns `STORAGE_FIELDS`; the role of new users must be assignable by the actor and not super-admin (`ProtectedActionException`, shown as a field error) |

## Config cache

`php artisan config:cache`, `php artisan optimize` and the maintenance page's "Rebuild caches" never apply the
stored settings while they build `bootstrap/cache/config.php` (`SiteSettings::buildingConfigCache()`,
switched by the console's `CommandStarting`/`CommandFinished` events in `HataServiceProvider`, and by
`SiteSettings::withoutApplying()` on the page). Laravel boots a fresh application to collect the config;
applying the settings to it would freeze them into the cache file: a setting removed later would keep its old
value, and the decrypted SMTP password and S3 secret would be written there. The cache holds the `.env`-level
values, and the stored settings are applied over them on every request as before. See
