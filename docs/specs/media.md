# Media library

> **Status: Parts 1–6 are built** (2026-11-12): the library (grid/list, search and filters, folders with a collapsible tree, moving and drag and drop, uploads with browser resize and server optimization, details, bulk actions and ZIP download, served by route with ULID keys), crop, replace, restore original and versioned URLs (Part 2), optimizing existing files (Part 3: engine, queue job, `media:optimize`, the page, the settings card), the media picker and logos from the library (Part 4), and S3-compatible storage with direct CDN URLs and moving files between disks (Part 5), and local raster images served as static files by the web server (Part 6: `public` disk, `DirectServing`, probe, fallback route; design record `docs/superpowers/specs/2026-11-12-media-direct-local-design.md`). Approved mockup: https://claude.ai/artifact/4ht3hKQ37R8oawQZFBCoi4 (8 screens). Design records of Parts 3–5 are in `docs/superpowers/specs/`; this file is the current behaviour.

A WordPress-like library of images and documents for pages, posts and themes. On top of WordPress: folders, crop, per-language alt text, "where is it used", automatic optimization on upload, and re-optimizing files already uploaded. It must work on shared hosting: no queue worker, no SSH on some hosts, PHP `memory_limit` 128 MB, GD only (Imagick may be missing).

## Why

Pages and posts (next stages) need cover images, inline images and downloadable files. Building media first means uploads are done once. The user's concrete case: someone uploads a 20 MB phone photo, and the site should store about 150 KB without them doing anything.

**Goals:** fast to find and reuse a file; nobody has to think about file size; nothing on the public site breaks when a file is optimized, cropped or moved.
**Non-goals (this stage):** video, responsive `srcset` sizes (themes stage), image filters/brightness, sharing folders per user, a public upload API.
**Anti-goals:** a slow page with hundreds of thumbnails at full size; a server crash (memory) on a big photo; URLs in published content that change after optimization.

## Public URLs and serving

`/media/{key}/{name}` (e.g. `/media/01JD8X4R…/price-list.pdf`) served by `MediaController` from the row's disk. Raster images of a site on "this server" live on the `public` disk and are fetched as static files by the web server once `php artisan storage:link` is in place and the probe confirmed it (decision 52, which supersedes decision 41 for them); without the link they are streamed by this route as before, so nothing breaks. SVG, documents and every kept original stay on the private `local` disk and go through the app. The key is a random ULID, so the library can't be listed by counting ids; anyone who has a link can open that file. No "private file" flag in this stage.

- The URL is stable: optimizing, cropping or replacing a file keeps `key`. If the extension changes (JPG → WebP) the old `{name}` 301-redirects to the current one, so links pasted before optimization keep working.
- Every generated URL carries `?v={version}` (`Media::url()`, `thumbUrl()`; `media.version`, starts at 1, bumped when the file's content changes through crop or replace). The `?v=` is how a changed file gets past browser caches while `{key}` stays the same.
- `Cache-Control: public, max-age=604800` only when `?v=` equals the current version. A stale or missing `v` gets `Cache-Control: no-cache` (always revalidated). Both carry `ETag` (path, size, version, updated_at) and `Last-Modified` (`304` on match). Not `immutable`.
- The old-name 301 keeps `v` (as sent, else the current version) and `thumb`.
- Permanent address and load (built 2026-11-12, performance review): when `media.show` redirects a raster image to its static or CDN URL, the 302 carries `Cache-Control: public, max-age=300` (`MediaController::STATIC_REDIRECT_SECONDS`), so a page that embeds permanent addresses starts PHP for an image at most once per five minutes per browser (or once per proxy), not on every view. It is safe: the target is found by key, not by name (the rename loop that keeps the old-name 301 uncacheable can't happen), a replaced file's old version stays for a week, and without the storage link the static address is answered by `media.static`. Signed-URL redirects and old-name redirects stay uncacheable.
- SVG gets the `Content-Security-Policy … sandbox` and `nosniff` headers. PDF is `inline`; DOCX/XLSX are `attachment`.
- `?thumb=1` serves the thumbnail (admin views).
- Content in pages/posts should store the media id, not the URL (decided in those specs).

## Storage disks (local and S3-compatible)

Built storage-agnostic, so files can live on the server or on S3 / Cloudflare R2 / Backblaze B2 / DigitalOcean Spaces / MinIO:

- All file access goes through `Storage::disk($media->disk)`; no `storage_path()` or local paths in media code. Each `media` row stores its own `disk`, so old files can stay on `local` while new ones go to S3.
- Private mode (`MEDIA_DISK=local` in `.env`, kept on purpose): every upload stays on the private `local` disk and everything is served through the app, so no link is needed; it is the escape hatch for a host where the link can never work. It is set only in `.env`: the Media tab offers "This server" (`public`) and S3, so saving the tab with "This server" stores `public`, which overrides `.env` and ends the private mode. While it is in effect the settings page shows no direct-serving status and no "other disk" callout or move link, and the move page counts no candidates and offers no move (`local` is not one of `MoveMediaToDisk::TARGETS`).
- New uploads go to the disk `MediaDisks::diskFor(config('media.disk'), $kind, $mime)` gives: with "this server" (`public`) raster images go to `public` and SVG and every non-image to the private `local` disk; with `s3` everything goes to `s3`. A row's original is on `MediaDisks::originalsDisk($media->disk)` (`local` for a `public` row, else the row's disk). The disk move uses the same rule (see "Move files between disks").
- Image processing reads the file into memory or a local temp file and writes the result back through the disk.
- Serving (built, Part 5): a local disk is streamed by `MediaController`. On a cloud disk: **SVG is always streamed** through the app (`readStream`, same CSP sandbox and `nosniff` headers), never redirected; **raster images** 302-redirect to the direct URL (`Storage::disk()->url($path)`, which includes the disk's path prefix) when the disk has a public/CDN URL, else to a signed `temporaryUrl()`; **documents and other files** always 302 to a signed URL whose `ResponseContentDisposition` (inline for PDF, attachment otherwise) and `ResponseContentType` carry the real file name. A signed URL is signed for the start of the current clock hour (`start_time` presign option) and expires two hours after it, so it is valid for at least an hour and every request within that hour gets the same URL (the browser can reuse the object it cached; a thumbnail grid doesn't refetch on every render). Redirects are never cached; the old-name 301 keeps `thumb`, `download` and `v`. `Media::url()`/`thumbUrl()` return the direct URL for cloud rasters with a public URL with `?v={version}` (the object path also carries the version, but rows moved or imported may not) and the app route with `?v=` for everything else, so a list can mix local and cloud rows. Download links use the app route with `?download=1`: local files get an `attachment` disposition with the real name, cloud files a 302 to a signed URL with `attachment` and the real name (`download` is ignored cross-origin); Open uses `url()`. A thumbnail is decided by what is served (WebP), so an SVG's thumbnail is direct on cloud. `Media::appUrl()` is the stable `/media/{key}/{name}` without `v`: the details panel's URL field and Copy use it, so content never holds a bucket URL. `SiteLogo` trusts the row on a cloud disk (no per-request `exists()`).
- Range: streamed responses (local files and cloud SVG) answer a single `Range: bytes=a-b` / `a-` / `-n` with `206` (`Content-Range`, `Content-Length`), `416` with `Content-Range: bytes */size` when unsatisfiable; every response sends `Accept-Ranges: bytes`; 206 and 416 send `Cache-Control: no-store`; HEAD opens no stream. Range logic lives in `App\Support\Media\ByteRange`. Multiple ranges and a non-matching `If-Range` send the whole file; `ETag`/`304` are checked first.
- The S3 adapter is `league/flysystem-aws-s3-v3`; the `s3` disk is in `config/filesystems.php` with `'throw' => false` (kept: every media read path handles a missing object as null/false, and the connection test builds its own disk with `'throw' => true`). Writes and deletes are therefore checked by their result: `MediaPaths::write()` (upload, rebuild) and the move's `writeStream()` throw `App\Exceptions\MediaWriteException` / `RuntimeException` on `false` inside the code's own try, so the usual rollback runs; `PruneMediaDeletions` treats a `false` delete like a thrown one (retry in 24 hours).
- **Write failures:** an upload the disk didn't store fails with "The file couldn’t be saved to the storage…" (`media.errors.storage_failed`, `MediaUploadException::storageFailed()`, the cause reported), writes no row and removes what it wrote. A crop, replace, restore or optimize whose write fails rolls back (old bytes back on shared local paths, new objects deleted), keeps the row at its version and schedules nothing; the crop page shows the same storage error, replace/restore a danger toast, and the optimize batch counts the file `unreadable`.
- **Locks need a shared cache store:** the per-row rebuild lock (`RebuildMediaFile::lockName()`) and the batch locks are cache locks, so web, queue and CLI must use the same store (database, redis, file on one server), never `array`. The version guard still stops a lost update, but only a shared lock keeps two writers off the same versioned paths.
- Moving existing files between disks (built): a second mode of the shared batch mechanism, see "Move files between disks" below; `media:move-disk {public|s3}` for SSH.
- **S3 settings live in the Media tab** (user's decision 2026-11-10): storage `public` ("This server") / `s3`, endpoint (empty = AWS), region, bucket, access key, secret key (encrypted with `APP_KEY` like the SMTP password, never shown back), "path-style endpoint" (MinIO), public/CDN URL. "Test connection" writes, reads and deletes a small file. Saving switches only where **new** uploads go; existing files move only through "Move to another disk". `SiteSettings` writes these over `filesystems.disks.s3.*` and `media.disk`.
- Built (every flow on a cloud disk, covered by `tests/Feature/Media/CloudDiskFlowsTest.php` on a faked `s3` disk): upload, crop, replace, restore, optimize-existing, ZIP download (each object copied with `readStream` into a temp file), the crop source preview (`MediaSource` reads the kept original, else the current file, through the disk), delete (objects removed at once) and the picker all go through the `Storage` disk API, never a local path (the only local reads are of the uploaded temp file). `Media::isEditable()` costs one `exists()` (a HEAD request) per instance, memoized, and is called only on single-file screens (details panel, crop page, source preview, `CropMedia`), never per row of a list.
- Built (object paths and write options, `App\Support\Media\MediaPaths`): `file($disk, $key, $version, $ext, $at)`, `thumb($disk, $key, $version)`, `original($disk, $key, $version, $ext)`. On a local disk (`MediaDisks::isCloud()` false) they are today's paths (`media/{Y/m}/{key}.{ext}`, `media/thumbs/{key}.webp`, `media/originals/{key}.{ext}`); on a cloud disk the name carries the version: `media/{Y/m}/{key}-v{version}.{ext}`, `media/thumbs/{key}-v{version}.webp`, `media/originals/{key}-v{version}.{ext}`, so a CDN that ignores `?v=` never serves a stale file and a page rendered before a rebuild keeps working. `writeOptions($disk, $mime)` is `['ContentType' => $mime, 'CacheControl' => 'public, max-age=604800']` on a cloud disk and `[]` on a local one; an SVG is written as an inert download instead (`ContentType: application/octet-stream`, `ContentDisposition: attachment`), so opening the object straight from the bucket or CDN can never run its script on that origin (the app always streams SVG itself with `image/svg+xml`, the CSP sandbox and `nosniff`). `write($storage, $disk, $path, $bytes, $mime)` puts with those options and throws `MediaWriteException` when the disk returns `false`; `UploadMedia` and `RebuildMediaFile` use it for every file, thumbnail (`image/webp`) and original (its own MIME). No ACL is set.
- Built (deferred deletion of replaced cloud objects): when `RebuildMediaFile::store()` replaces objects on a cloud disk, the ones the new version doesn't use are recorded in `media_pending_deletions` (`App\Models\MediaPendingDeletion`: `disk`, `path`, `delete_after` = now + 7 days, indexed), inside the same transaction as the row update, instead of being deleted after commit (local files are still deleted after commit). A failed or refused rebuild records nothing. `App\Actions\Media\PruneMediaDeletions::handle($limit = 200)` deletes the due rows' objects, oldest first (a missing object is fine), skips any path a `media` row on that disk still points at, and removes the rows; it returns the number of rows removed. When a disk's delete throws or returns `false`, its rows are reported and retried 24 hours later, so they don't block the rows behind them. It runs from `media:prune-deleted` (loops until nothing is due; scheduled `daily()` in `routes/console.php`), at the end of every optimize or move batch that still has budget left (50 rows, `MediaBatchEngine::processBatch()`, so browser, queue and CLI drivers of both modes prune; a batch that spent its budget skips it so a browser tick answers at once; an error is reported, never fails the batch), and from the library page `mount()` at most once an hour (`Cache::add('media-prune-deletions', …, 1 hour)`, 50 rows, run with `defer()` after the response, errors reported). No worker or cron is needed: 7 days is a minimum. Deleting a media row (`DeleteMedia`, `DeleteFolder`) still deletes its current objects at once after commit, on any disk: the disk and paths are re-read with `lockForUpdate()` inside the delete's transaction, so a move or rebuild committed after the rows were loaded never leaves its objects orphaned. When a rebuild on a cloud disk is refused because another one committed the row meanwhile (its 120 s row lock expired), the rollback skips every path the stored row now points at, so the winner's objects stay.
- **SVG on a cloud disk:** always streamed through the app with the CSP sandbox and `nosniff` (never redirected), and stored as `application/octet-stream` + `attachment` (see `writeOptions()`), so even a direct bucket/CDN link to the object downloads it instead of rendering it.

## Upload

- Anywhere on the library page: drag-and-drop overlay (screen 2), the "Upload files" button, or the "Upload new" tab in the picker. Many files at once, sequentially (one at a time, so the hosting isn't hit in parallel).
- Allowed (user's decision 2026-11-10), checked by extension **and** detected MIME type (plus magic bytes in the first 8 KB for generically detected types; an SVG must have an `<svg` root after any XML declaration, comments or DOCTYPE within those 8 KB):
  - **Images:** JPG, PNG, WebP, GIF, SVG, AVIF, HEIC/HEIF. HEIC is converted to JPEG in the browser (Safari) or on the server (Imagick that can decode HEIC: to WebP, or JPEG when the format setting keeps the original, even with optimization off); it is never stored as HEIC, because browsers can't show it. If neither can convert it (or it is too large for the server's memory), the upload fails with "HEIC can't be converted on this server, export the photo as JPG". AVIF is stored as is when the driver can't decode it (no thumbnail, an icon instead).
  - **Documents:** PDF, DOCX, XLSX, PPTX, DOC, XLS, PPT, ODT, ODS, ODP, TXT, CSV, RTF.
  - **Other:** ZIP, MP3. Stored and served for download only, no processing.
  - The type filter in the library: all / images / documents / other.
- Route: `GET /media/{key}/{name}` (`media.show`, `MediaController`), public (no auth). The route is excluded from the `web` middleware group (`->withoutMiddleware('web')`, 2026-11-12), so serving a file starts no session, sets no cookie and runs no CSRF or locale middleware; its 404 page is therefore rendered in the site's default language. The key is a ULID (stored uppercase; the route accepts either case and upper-cases it before the lookup, so SQLite and MySQL agree). An old `{name}` gets a 301 to the current URL (`?thumb=1` kept); `?thumb=1` serves the thumbnail (404 without one); a missing row or file is 404. The 301 and the cloud 302 are sent with `Cache-Control: no-cache, must-revalidate, max-age=0`, so a rename A to B to A can't loop in a browser. A disk counts as local when its configured driver is `local` (not by name); any other driver gets the 302. Local files are streamed with `Cache-Control: public, max-age=604800`, `ETag`, `Last-Modified` (`If-None-Match` gets a 304), `X-Content-Type-Options: nosniff` on every response including redirects and 304s, and SVG also gets the CSP sandbox (`default-src 'none'; style-src 'unsafe-inline'; sandbox`).
- Static address (`media.static`, `GET /storage/media/{path}`, `StaticMediaFallbackController`, also without `web` middleware): the fallback for static image URLs when the `public/storage` link is missing (with the link, the web server answers them itself). It takes the ULID from the file name (`{key}-v{n}.{ext}` or `thumbs/{key}-v{n}.webp`, key in uppercase) and finds the row with one query on the unique `key` index; the row must be on the `public` disk and a raster image (not SVG), and the requested path must equal its `path` or `thumb_path` exactly, which is what is streamed (always `public, max-age=604800`, since the name carries the version). A request for an older version of the same key (HTML cached before a crop or replace) gets an uncacheable 302 (`no-cache, must-revalidate, max-age=0`) to the row's current file or thumbnail on this same route, not to `media.show`, which could send it back to the broken link. Anything else is 404: a name without a key, a lowercase key, trailing junk, a version that does not exist yet, a `..` segment, an SVG or document, a row on another disk, a thumbnail the row no longer has, or a missing file; it never reads the private disk. `media.show` for a public raster with direct serving active 302-redirects (uncacheable) to the static URL (`?download=1` still streams); with direct serving inactive it streams as before. Both controllers share the streaming code (`Concerns\StreamsMediaFile`: ETag, HEAD, ranges). The private `local` disk's `serve` route is off, since its `/storage/{path}` would claim these URLs.
- Web server caching (built): static files get their cache headers from the web server, not the app. `public/.htaccess` sends `Cache-Control: public, max-age=604800` and `X-Content-Type-Options: nosniff` for webp, jpg, jpeg, png, gif and avif under `storage/media/` (the path test assumes the site is at the domain root; guarded by `IfModule mod_headers.c`, no other path is touched); nginx needs the `location ^~ /storage/media/` block from the README, which also falls back to Laravel (`try_files $uri /index.php?$query_string`) so `media.static` answers when the file or link is missing. The paths carry the version, so a week of caching never shows a stale picture.
- Probe (built, Task 6 of the direct-serving work, reworked in the final fixes): the browser proves that the static URL works, since only it knows what the web server does. `DirectServing::probeSize()` reads `media/probe.png` on the `public` disk once per process; when it is missing or not a probe image it writes a new one, a hand-built greyscale PNG (`DirectServing::probeImage()`, no image extension needed) whose width and height are random between 2 and 64 px, and deletes the legacy text probe `media/.probe`. The name is not a dotfile, because Laravel's standard nginx config denies dotfiles. The layout (`partials/media-direct-probe`) sets `window.mediaDirectProbe = {url, width, height, report, csrf, auto}` only for a user with `settings.edit` while the site disk publishes files and `DirectServing::dueForCheck()`, and then records the attempt (`markAttempt()`: `media_direct_attempted_at`/`_url`); a probe image that can't be written is reported at most once an hour (cache key `media-direct-probe-failed`) and the config skipped. `resources/js/media-direct-probe.js` loads `url` with `new Image()` and a cache-busting `check` query (the way an `<img>` loads, so no CORS: another host, `www` vs apex or http vs https can't give a false failure), compares `naturalWidth`/`naturalHeight` with the expected size (15 s timeout), and POSTs `{ok, url, force}` with the `X-CSRF-TOKEN` header from `csrf` to `POST /admin/media/direct-check` (`admin.media.direct-check`, `MediaDirectCheckController`, admin group plus `can:settings.edit`, `ok` boolean and `url` string required, `force` optional boolean), once per full page load and after `livewire:navigated` while the config is present. The endpoint records the result against the public disk's base URL only when `url` equals `probeUrl()`; it answers `{state}`, and the script then fires a `media-direct-checked` window event with `{state}`. `window.checkMediaDirect(force)` probes on demand with the config on the page (even without `auto`) and resolves to the new state.
- Probe backoff (built): `dueForCheck()` is false while the link is missing and for 30 minutes (`RETRY_MINUTES`) after an attempt for the current public URL (an automatic probe handed out, or a recorded result), even when its report never arrived; otherwise it is true while the state is `unchecked` or `unreachable`, and in `direct` once the last confirmation is 24 hours old (`RECHECK_HOURS`). A changed public URL is due at once. `record($ok, $url, $force)` writes nothing when the same result for the same URL was stored less than 30 minutes ago, unless `force` ("Check again", and the check after creating the link). Its writes, and `markAttempt()`'s, go through `SiteSettings::putStoredOnly()`: the stored-only keys only, then the settings cache and the in-process copy are refreshed, with no `apply()`, so no logo cache flush, no mailer reset and no config rewrite. So a settings editor's page view costs at most one small write per 30 minutes while direct serving is not confirmed, and one per day once it is.
- Storage link: `CreateStorageLink::handle($actor)` (`settings.edit`) runs `storage:link --force` (replaces a stale symlink; Laravel never replaces a real directory in its place, which then fails), forgets the memoized link check (`DirectServing::refresh()`) and throws `StorageLinkException` (`media.storage.direct.link_failed`, naming `php artisan storage:link --force`) when the link still doesn't resolve to the `public` disk root; success text is `media.storage.direct.link_created`. The status line and its two buttons are on the settings Media tab (site-settings.md → Direct serving status). Library warning: for a user with `settings.edit`, while the site disk publishes files and the state is `link_missing` or `unreachable`, the library page shows a warning callout (`media.index.direct_warning`) linking to `admin.settings.edit?tab=media`; `unchecked` and `direct` show nothing.
- Request cost of static URLs (built): `SiteSettings::stored()` is read from the cache once per process (request, command, queue job) and kept in memory until `apply()` or a write, and `DirectServing` checks the link once per process (a few `stat` calls; `refresh()` forgets it, and `Queue::before` calls it so a long-lived worker sees a removed link). So `Media::url()`/`thumbUrl()` cost no query, cache read or file stat after the first call of a request, and documents and SVG never ask `DirectServing` at all.
- Serving per type: images and PDF `inline`; MP3 `inline` (plays in the browser); everything else `attachment`. TXT/CSV are sent as `text/plain` attachments with `nosniff`, so a file can never run as a page.

### Optimization on upload

Two steps, because a 6000×4000 photo needs ~100+ MB of memory to decode on the server:

1. **In the browser** (when "Compress in the browser" and "Optimize images" are both on): JPG/PNG/WebP (and HEIC when the browser can decode it, i.e. Safari) are drawn to a canvas with EXIF orientation applied and scaled down to **3840 px** on the long side (not to `max_side`, so the kept original still allows 4K and better crops), then exported as JPEG at quality 0.92 (light, the server does the real compression); a PNG or WebP with transparency is exported as PNG instead. Only images over 3840 px are redrawn, except HEIC/HEIF, which is always converted when the browser can decode it. The file keeps its name with the new extension. GIF, SVG and other files are sent as they are. If the browser can't do it, the original file is sent. The browser also sends the size of the file the user picked; it's stored as `original_size` (the "18.4 MB" in "18.4 MB → 164 KB"), and the picked file's extension, stored as `uploaded_extension` when it is on the whitelist (so a HEIC converted to JPEG still reads "uploaded as HEIC"; anything else falls back to the received file's extension).
   - The size limits (30 MB / 20 MB) apply to the file the user picked and are checked in the browser first (instant error on the tile); the server checks what arrives against the same limit and against PHP's `upload_max_filesize`. The browser also checks the file as it will be sent against the PHP cap: a file the browser won't shrink (documents, GIF, SVG, or any file while browser resizing is off) is prechecked against `min(kind limit, cap)`, and a shrinkable image is checked against the cap after shrinking, just before upload. Both use the "File is too large" text with the limit that applied.
2. **On the server** (`OptimizeImage`, built on Laravel's own `Illuminate\Image` / `Image` facade, e.g. `Image::fromUpload($file)->orient()->scale(2560, 2560)->optimize('webp', 80)`; driver `images.default` set to `imagick` when the extension is loaded, else `gd`; the framework's GD/Imagick drivers run on `intervention/image` ^4.2): orient, scale down to max side, encode to WebP (or keep JPG/PNG when the setting says so) at the chosen quality, strip metadata when "Remove EXIF" is on. If the result isn't smaller than the input, the input is kept, unless the image was scaled down or "Remove EXIF" is on and the input carries EXIF (then the result is used). Animated images (GIF, WebP, APNG) and SVG are never re-encoded. HEIC/HEIF dimensions come from an Imagick header ping (PHP's `getimagesize` can't read them). HEIC/HEIF is always converted (`OptimizeImage::MUST_CONVERT`): to WebP, or to JPEG when the format is "original"; with optimization off it is still converted to WebP (no scaling, no EXIF step), and the "keep the input when not smaller" rule never applies to it. `UploadMedia` refuses with `heic_unsupported` whenever the result is still HEIC/HEIF (GD, an Imagick that can't decode it, or too large for memory). Before decoding, the server estimates the memory needed (width × height × 4 × overhead, from the header without decoding) against what's left under `memory_limit`. If it won't fit, the file is **stored as it is** (user's decision 2026-11-10): `optimized_with = null`, the upload tile and the details panel say "Not optimized: too large for the server to process", and it stays a candidate on the "Optimize existing" page, which skips it with the same reason while memory is still short. Any other decoding error is handled the same way.
3. A 400 px WebP thumbnail is made for every raster image.

If "Keep originals" is on (and optimization is on), the uploaded file (after the browser step) is stored as `original_path`.

Malformed edits throw `InvalidArgumentException`.
- With an original kept, the crop/rotate/flip is stored in `edits` and re-applied whenever the file is rebuilt (optimizing existing files, a settings change), so re-optimizing never undoes a crop. ## Optimize existing files (screen 8)

- Candidates: raster images (not animated GIF/WebP/APNG, not SVG) whose `optimized_with` differs from the current settings fingerprint.
- No queue worker, so the page processes them in batches while it's open: `wire:poll` calls `processBatch()`, which handles files for at most ~5 seconds per request. Progress (cursor = last processed id, counts, bytes saved, skipped) is stored in the `settings` table under `media_optimization_run`, so closing the tab and coming back resumes where it stopped. Pause stops polling; Stop clears the run.
- Each file: from the original if kept, else from the current file. From a kept original the result is always written, even when it is bigger than the current file; from the current file, a result the optimizer kept unchanged (not smaller) is "already optimal": no write, only the fingerprint is recorded. URL and id stay.
- Shows: processed / total, time left (from the average so far), MB saved, average saving, skipped count, the last files with before → after.
- An artisan command `media:optimize` does the same for anyone with SSH (output in English, decision 17).
- Built (the engine, `App\Actions\Media\OptimizeExistingMedia`): `start($actor)` authorizes `MediaPolicy::optimize` (`media.edit`) and calls `startWithoutActor()` (the CLI, like decision 16), which replaces any run with a fresh `running` one (`id` = a new ULID, `total` = candidate count, the current fingerprint, cursor 0, `heartbeatAt` = now). With optimization off both throw `App\Exceptions\OptimizationDisabledException` and save nothing (such a run could never move); callers check `media.optimize.enabled` first and show their own message. `pause()` (running → paused), `resume()` (paused → running, `heartbeatAt` = now, so a "queue isn't running" fallback counts from the resume), `stop()` (clears the run). `processBatch($driver, $budgetSeconds)` returns null without a run and does nothing (returns the run) when it isn't `running`, is stale, or `Cache::lock('media-optimization-batch', ceil(budget) + 60)` is held by another batch; a `running` run that finds optimization off (before the batch, or before its next file) is paused instead, so every driver stops and the page and the settings card show "Paused", and Resume continues it once optimization is on again; otherwise it re-reads the run under the lock, processes candidates with id > cursor until the budget is spent (checked after each file, so at least one), sets `heartbeatAt`, `driver` and `secondsSpent`, marks the run `done` when no candidate is left and saves it. Before each file the batch saves its id as `in_progress` on the run (and clears it after); if the process dies on a file (e.g. a memory fatal `MemoryGuard` missed), the next batch finds that id as the next candidate and records it as unreadable without trying it again. A run stopped or replaced during the batch is not overwritten (runs are told apart by `id`, so one replaced within the same second counts too), nor one whose cursor another batch moved past the cursor this batch last saved (the lock expired mid-batch); a pause made during the batch is kept and stops the batch before its next file. Each candidate is visited once per run (the cursor), so skipped files can't loop it. An unexpected error on one file (e.g. a disk write; `RebuildMediaFile` rolls it back) is reported and counted as unreadable so the run moves on.
- Built (one file, `optimizeOne($media)` → `[OptimizeOutcome, bytesBefore, bytesAfter]`): source `MediaSource::for()` (none readable → `missing`); `OptimizeImage::handle()` with the stored `edits`; a failure (`too_large` → `too_large`, any other or malformed edits → `unreadable`) or a result still HEIC writes nothing and the file stays a candidate; when the source is the current file and the bytes came back unchanged, `RebuildMediaFile::markOptimized()` (`already_optimal`, no write, no version bump); otherwise `RebuildMediaFile::store()` (`optimized`, version +1, same key). Both pass the version loaded with the row: a file cropped or replaced while the batch processed it is recorded as `changed` (skipped; that change is kept, never undone), one deleted meanwhile as `missing`, with no files left behind. The stored `edits` are applied (and kept) only when the source is the kept original; when the original file is gone, the current file already has them baked in, so they are not applied again and `edits` is cleared (also on "already optimal"). Without a kept original, while optimization and "Keep originals" are on, the current bytes become the original first. An existing original is never dropped. From a kept original the result is written even when it is bigger than the current file (bytes after can exceed bytes before).
- Built (the queue job, `App\Jobs\OptimizeExistingMediaBatch`): `ShouldQueue`, `timeout` 60, `tries` 1, `BUDGET` 45 seconds. Each job carries the `runId` it was queued for (the page dispatches it with the stored run's id, re-dispatches pass it on) and returns at once, without re-dispatching, when the stored run has another id (stopped and started again, or `media:optimize --restart`), so the chain of an old run dies out instead of running beside the new one. `handle()` calls `processBatch('queue', BUDGET)` and, when the returned run is `running` and not stale (the engine marks it `done` when no candidate is left), dispatches itself again. Not `ShouldBeUnique`: the engine's batch lock keeps two batches from overlapping; with no run, or a paused/stale run, it does nothing and doesn't re-dispatch. When the batch moved nothing (the run is unchanged, because another batch holds the lock) it re-dispatches with a 10 second delay instead of at once. While optimization is off it never re-dispatches (the engine has paused the run). A worker boots once, so `AppServiceProvider` re-applies the site settings before every queued job (`Queue::before` → `SiteSettings::apply()`, skipped on the `sync` connection; decision 48): settings saved in the admin (quality, keep originals, turning optimization off, …) reach a long-running `queue:work` at its next job.
- Built (the command): `php artisan media:optimize [--restart]`. With optimization off it prints "Optimization is off in the media settings." and exits 1. Without `--restart` it resumes a `running` or `paused`, non-stale run (`resume()`); otherwise (no run, done, stale, or `--restart`) it calls `startWithoutActor()`. It then loops `processBatch('cli', 5.0)`, re-applying the site settings (`SiteSettings::apply()`) before each batch so a change saved in the admin reaches it; when a batch pauses the run because optimization was turned off it prints "Optimization is off in the media settings." and exits 1. After each batch it prints `Processed N/T · saved X MB · skipped K` after each batch (saved = bytes before minus after of the files rewritten, signed, so a bigger result shows as negative; skipped = processed minus optimized). The loop ends when no run is returned, the run is no longer `running` (done, paused or stopped from the browser meanwhile) or has gone stale; when a batch moves nothing (another batch holds the lock) it sleeps 1 second without printing, and after 120 such waits exits 1 with "Another batch is running; try again later."; otherwise it prints a summary table with the count per outcome and the total bytes. Exits 0.
- Built (the page, `pages::admin.media.optimize`, `GET /admin/media/optimize`, `admin.media.optimize`, `can:media.edit`, registered before the `media/{media}/…` routes; linked from the "Optimize existing" card on the Media settings tab): state `bool $browserFallback`, computed `run`, `candidateCount`, `queueAvailable` (`queue.default !== 'sync'`), `isStale`. Idle: candidate count (not shown while optimization is off: there are no candidates then) and "Start" (disabled when optimization is off or nothing matches); with optimization off a callout links to `admin.settings.edit?tab=media`. `start()` calls `OptimizeExistingMedia::start()` and, when a queue is configured, dispatches `OptimizeExistingMediaBatch`; `resume()` does the same; `pause()`, `stop()` (behind `<x-confirm-modal>`), `startOver()` (= `start()`, for a stale run). While the run is `running` and not stale the page polls `tick()` every 2 seconds with `wire:poll.2s.keep-alive` (browsers throttle polling in background tabs, and in browser mode the tab is what processes the files; the browser-mode note asks to keep the tab open and in the foreground). With optimization off `tick()` calls `processBatch()` in any mode, which pauses the run. Otherwise: with no queue (or in fallback) it calls `processBatch('browser', 5.0)`; with a queue it only refreshes, and when the run's heartbeat (its start when none yet) is older than 30 seconds and no batch holds the lock (`OptimizeExistingMedia::isBatchRunning()`, which probes by taking and at once releasing the lock) it sets `browserFallback` (`#[Locked]`), shows "The queue isn't processing jobs, continuing in this tab" and processes in the tab from then on; a reload starts in browser mode only without a queue; the engine lock keeps the two from colliding. The engine refreshes `heartbeatAt` before every file, so a long queue batch counts as alive. Starting with optimization off shows a danger toast. Running or paused: progress bar, "N of M files" (pluralized by M with `trans_choice`, also on the settings card), time left (`OptimizationRun::secondsLeft()`), net saved (`+N MB` when files grew), average saving, skipped count with reasons (already optimal, too large, unreadable, missing, changed meanwhile), the latest 10 files (before → after, outcome badge), Pause/Resume/Stop, and a note that the tab may be closed (queue) or must stay open (browser). Stale: a callout and "Start over". Done: summary and "Start a new run" while candidates remain. `OptimizationRun::skipped()` and `bytesSaved()` are shared with the command.
- Built (shared mechanics, used by this page and "Move files between disks"): the run state, lock, in-progress marker, heartbeat, budgets, pause/resume/stop and the end-of-batch prune live in `App\Actions\Media\MediaBatchEngine` (template methods: `runs()`, `lockName()`, `isProcessable()`, `next()`, `processFile()`, `recordAbandoned()`, `mustPause()`; public `current()`, `canProcess()`, `isBatchRunning()`), the run fields in `App\Support\Media\MediaBatchRun` (`OptimizationRun` adds `fingerprint` and bytes before/after), the settings-row store in `MediaBatchRunStore` (one row per mode), the queue job in `App\Jobs\MediaBatchJob` (`OptimizeExistingMediaBatch` adds only its engine), the CLI loop in `App\Console\Commands\MediaBatchCommand` and the page logic (driver choice, fallback, tick, start/pause/resume/stop) in `App\Livewire\Admin\MediaBatchPage`. Each mode has its own lock, so an optimize batch and a move batch can run at the same time; the per-row rebuild lock and the version guard keep them off the same file.
- `OptimizationRunStore::get()` treats a malformed stored run (unknown status, missing id/cursor/total/fingerprint, unparseable dates) as no run, so the page and the command never fail on a corrupt row. A run saved before runs had an `id` counts as malformed: it shows as no run and a new one can be started (runs are short-lived progress, nothing is lost but the counters).

## Move files between disks

- Targets: `MoveMediaToDisk::TARGETS` = `public` ("This server") and `s3`. Moving everything to the private `local` disk is not a direction (refused like an unknown disk); while the configured storage is `local` (private mode) the page's `candidateCount` is 0, so it says there is nothing to move and its start button stays disabled.
- Placement: `MoveMediaToDisk::destinationFor($media, $target)` = `MediaDisks::diskFor($target, $kind, $mime)`, the upload rule: to `public`, raster images (kind image, not SVG) go to `public` with their original on `local`, SVG and every non-image to `local`; to `s3` everything goes to `s3`, the original gathered from wherever it is (`$media->originalsDisk()`).
- Candidates (`MoveMediaToDisk::candidates($target)`, one query used by the run total, `next()`, the page count and so the command): every row whose `disk` differs from `destinationFor()`, by ascending id. For `public`: (`disk != 'public'` and raster) or (`disk != 'local'` and not raster), the raster test being `MediaDisks::isRasterImage()` in SQL; for `s3`: `disk != 's3'`. A raster on `public` whose original is on `local` is where it belongs; where a row's original is never makes it a candidate. During a move uploads keep working: new files go to the configured disk (`media.disk`); a new row on the other disk with a higher id is picked up by the same run.
- Built (the engine, `App\Actions\Media\MoveMediaToDisk`, on `MediaBatchEngine`): `start($actor, $target)` authorizes `MediaPolicy::moveToDisk` (`media.edit`) and calls `startWithoutActor($target)` (the CLI), which throws `InvalidArgumentException` for an unknown disk or a cloud disk without a bucket and otherwise replaces any move with a fresh `running` one (`total` = candidates). Run state `App\Support\Media\DiskMoveRun` (`target`, `bytesMoved`; recent entries `name`, `size`, `outcome`) in the settings row `media_move_run` (`DiskMoveRunStore`), lock `media-move-batch`. Pause, resume, stop, in-progress marker (a file the process died on is recorded `failed`), heartbeat, budgets and prune as for optimization. A move run never goes stale and is never paused by a setting.
- Built (one file, `moveOne($media, $target)` → `App\Enums\MoveOutcome`: `moved`, `missing`, `failed`, `changed`; never throws): takes the row's rebuild lock (`RebuildMediaFile::lockName()`, for `rowLockSeconds()`: `MoveMediaToDisk::FILE_SECONDS` = 1800 s in the CLI, the batch's file time in the browser (60 s) and the clamped queue time (below) in the queue; held by a crop/replace/restore/optimize of the same row → `changed`); re-reads the row (gone → `missing`; another version or disk → `changed`); a row already on its destination → `changed` (nothing moved, counted as skipped; the batch never picks one); the current file missing on the source disk → `missing`. Copies the file and thumbnail from the row's disk to the destination, and the original from the row's originals disk to the destination's originals disk (`MediaDisks::originalsDisk()`), with `readStream` → `writeStream` (never loaded whole; `MediaPaths::writeOptions()` on a cloud disk: content type, cache header) to the `MediaPaths` paths of version + 1 named with the destination (versioned names on `s3` and `public`, the original's too, since it is named with the row's disk; today's names when the destination is `local`), and checks each copy's size against the source. An SVG is never copied to a publishing disk (`MediaWriteException`, the same guard as `MediaPaths::write()`). A missing thumbnail or original is dropped (column set to null). Then, in a transaction that re-reads the version with `lockForUpdate()` (gone → `missing`, other → `changed`), switches `disk`, the three paths and `version + 1`. The version goes up so `?v=` changes and a row moved back to a cloud disk never reuses an object path still waiting for its deferred deletion. Each old object follows the rule of the disk it was on: on a disk that versions its paths (`s3`, `public`) it is recorded as a pending deletion (7 days) in that transaction (pages, static links and CDN caches may still point at it); on `local` it is deleted after commit. So a `public` image moved to S3 keeps its public file and thumbnail for 7 days while its private original goes at once. Any failure (read, write, size, transaction) deletes every copy written, restores the instance's attributes and leaves the row and its old files untouched; an unexpected error is reported and counted as `failed`.
- Built (copies of a dead process): before copying, each new path is recorded in `media_pending_deletions` on the disk it is written to (the destination, or `local` for the original of a `public` row), due in `INSURANCE_HOURS` (24); the commit transaction drops those rows, and so does a caught failure for every copy it removed (a copy it couldn't remove keeps its row). A process killed mid-copy (PHP time limit, worker timeout, deploy) leaves its rows, and the prune sweeps its partial copies a day later; a path a `media` row points at is never deleted. Around the copy the move calls `set_time_limit(0)` (for the rest of that request or job) and `ignore_user_abort(true)` (restored afterwards), so a browser tick isn't cut off by `max_execution_time` or a closed tab. Very large files are still best moved with `media:move-disk` (the page says so).
- Built (the queue job, `App\Jobs\MoveMediaBatch`): the shared `MediaBatchJob` (runId, `BUDGET` 45 s, 10 s delay when nothing moved, stops when the run is replaced, done or paused). Its `$timeout` is the engine's queue batch lock, `lockSeconds(BUDGET, 'queue', $connection)`: budget + `FILE_SECONDS` (1845 s), clamped to `retry_after - 10` of the job's connection (`config("queue.connections.{$connection}.retry_after")`, floor 15 s, no clamp when the connection has none), so with the stock 90 s it is 80 s and a second worker is never handed a job that still runs (the timeout is recomputed in `onConnection()`). The queue batch's lock and its per-row lock use the same clamped value; the browser's batch lock is budget + 60 s (like optimization), so it never outlives a request; only the CLI keeps `FILE_SECONDS` (it has no time limit). `MediaBatchEngine::lockSeconds($budget, $driver)` and `fileSeconds($driver)` take the driver. A file that outlives the job is killed; the in-progress marker makes the next batch abandon it (counted as failed) and the insurance rows sweep its partial copies. Very large files should be moved with `media:move-disk`, which has no time limit.
- Built (the command): `php artisan media:move-disk {to} [--restart]`. Prints the engine's message and exits 1 for an unknown or unconfigured disk. `{to}` is `public` or `s3`; anything else (`local` too) prints "Unknown disk [x]; use one of: public, s3." Resumes a `running`/`paused` move to the same disk, else starts a new one ("Starting a new move to This server (public): N file(s) to move.", the storage named by its English `site_settings.media.storage.*` label). Loops 5-second batches like `media:optimize` (settings re-applied before each, 120 idle waits then "Another batch is running; try again later."), printing `Moved N/T · X MB · skipped K`, then "Done." or "The move was paused." and a table per outcome.
- Built (the page, `pages::admin.media.move`, `GET /admin/media/move`, `admin.media.move`, `can:media.edit`, before the `media/{media}/…` routes; linked from the "N files are not stored where new files go" callout on the Media settings tab): on `MediaBatchPage` like the optimize page (same driver choice, 30-second fallback, keep-alive poll, pause/resume/stop with `<x-confirm-modal>`). Candidates (`MoveMediaToDisk::candidates()`) are counted against the target of a running or paused move, else (no move, or a finished one) the configured storage (`media.disk`), which is also where "Start moving" / "Start a new move" go, so "N files … still on the other disk" and the new move always mean the same disk; each card shows its disk as "Files go to: {storage}" (the progress card its run's). Idle: candidate count, "Start moving" (disabled with none) and the note that very large files are best moved with `php artisan media:move-disk`. Running/paused: progress, time left, moved count, data moved, skipped with reasons (missing, failed to copy, changed meanwhile), the latest 10 files (size, outcome badge), the tab note, "Uploads keep working during the move" and the large-files note. Labels both batch pages share (back, pause/resume/stop, progress, time left, latest files, the tab notes, the fallback) are `media.batch.*`. Done: "Start a new move" while files remain on the other disk.

## Calls made without the user (check these)

- Folders nest to any depth; one folder per file. No trash: deletion is final after the confirmation.
- Raster images on "this server" are static files of the `public` disk (needs `storage:link`); until the link exists and a browser probe confirmed it, a fresh install serves them through the route at the cost of PHP handling each image request. The first administrator page view runs the probe. Everything else (SVG, documents, originals) always goes through the app.
- Old URL after JPG → WebP redirects (301) instead of keeping the `.jpg` name. Any other `{name}` for a valid key also redirects to the current one.
- Originals kept by default; "Apply" crop edits the file everywhere it's used.
- Only a 400 px thumbnail now; responsive sizes wait for the themes stage.
- 40 per page with "Show more" in the grid (up to 400), 25 in the list.
- Uploads go one at a time.
- Crops are stored as parameters and re-applied when a file is rebuilt from its original.
- The browser scales to 3840 px before upload; that file is the kept "original". Full camera resolution is not kept.
- `original_size` is the size of the file the user picked (reported by the browser); limits apply to that file.
- "Download ZIP" is capped at 100 files per archive (no size cap; the archive is a temp file sent by a plain route).
- An upload goes into the folder that was open when the file was queued, even if the user switches folders while the queue runs; if that folder is deleted meanwhile, the file fails with an error instead of landing elsewhere.
- A PNG or WebP with transparency stays PNG after browser resizing (the plan named only PNG), so WebP transparency isn't lost to JPEG.
- Crop works on a preview of the source scaled to at most 2048 px; the browser sends fractions and the server converts them to source pixels (`CropMedia::cropPixels`), so a big original never has to reach the browser.
- A crop without a kept original is baked into the file (`edits` null) and can't be undone; the page says so before Apply.
- Edits are applied in a fixed order: rotate, flip horizontally, flip vertically, crop, exact size, then the max-side scale.
- Replace works only within the same kind (image for image) and not across the raster/SVG line, and the name follows the new file; the old name 301-redirects.
- "Restore original" clears the stored edits, so it also undoes crops and rotation.
- "Save as copy" needs `media.upload` and isn't confirmed, since it changes nothing that exists; "Apply" and replace are confirmed because they change the file everywhere it's used.
- The crop page uses a full-screen layout (`layouts::focus`) without the sidebar.
- Changed files get a new `?v=` instead of a new key, so URLs stored in content stay valid.

The library's filters (search, type, month, folder / no folder, unused, optional extensions: only plain `[a-z0-9]` extensions are matched, by a `LIKE '%.ext'` with no escape clause, so the same SQL runs on SQLite and MySQL) live in `App\Support\Media\MediaFilters`, which the library page's `filteredQuery()` and the media picker both use; `MediaFilters::monthRange()` turns a `YYYY-MM` month in the site timezone into a UTC range.

## Known limitations

- A cached permanent-address redirect (5 minutes) can point at a file that has just been moved to another disk or deleted; the image is missing for that browser until the redirect expires.
- Partial renders are covered by feature tests of the server's answer; there is no real-browser test of the morphing itself. The narrowing leans on two Livewire internals: the public trait method `triggerImplicitIslandRender()` and the shape of the update payload (`isOnlyChange()`); check both after a Livewire update (`MediaPartialRenderTest` fails if either changes).
- Buttons inside the islands call `$wire` from Alpine, so they don't get Livewire's `data-loading` state.
- A file whose copy takes longer than a queue batch's clamped timeout (about 80 s with the stock `retry_after`) or a browser request's time is killed, abandoned by the next batch and counted as failed; move such files (videos, big archives) with `media:move-disk`, which has no time limit.
- Moves call `set_time_limit(0)` and `ignore_user_abort(true)` around each copy, only when the functions exist (a host can list them in `disable_functions`). Without them the browser mode can still be cut off by `max_execution_time` or a closed tab; the insurance rows then clean up the partial copy after a day.
- SVG objects stored on a bucket before they were written as `application/octet-stream` + `attachment` keep `image/svg+xml`. The app never redirects to them, but a direct bucket or CDN link to such an object renders it on that origin until the file is rebuilt or moved again.
- When deleting an object fails (a cleanup after a failed write or a rolled-back rebuild), the object can be left in the bucket without a row. Deferred deletions and the move insurance are retried by the prune, but a failed cleanup that was never recorded is not.
