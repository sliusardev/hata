# Project notes for Claude Code

Hata is a Composer package (`sliusardev/hata`, namespace `Hata\`): a content management framework (CMF) for Laravel, with an admin panel (users, roles, permissions, site settings, media library, maintenance, content types with public pages). A client site is a fresh Laravel app that requires it and runs `php artisan hata:install`. This repository is the package; the app to look at it in a browser is the demo at `/Users/vitalii/Herd/hata-demo` (https://hata.test), which requires this checkout through a Composer path repository (symlink), so an edit here shows there at once. Laravel Boost (its guidelines, MCP server, `AGENTS.md`) is installed in the demo, not here. Install, update and the extension API: [docs/specs/package.md](docs/specs/package.md).

## Package structure

- **Layout:** `src/` (`Hata\`), `config/hata.php` (the one published config; `config/internal/` holds the language catalogue and the permission groups, never published), `database/{migrations,factories,seeders}` (`Hata\Database\…`), `resources/{views,lang,lang-framework,css,js,static}`, `routes/{web,admin,settings}.php`, `dist/` (built assets, committed), `stubs/` (installer stubs and `htaccess`), `tests/` (Pest on Testbench), `workbench/` (the test host's `App\Models\User`, its factory, seeders and `WorkbenchServiceProvider` with the host defaults).
- **Service provider:** `Hata\HataServiceProvider` (auto-discovered) does what the app's `AppServiceProvider`, `bootstrap/app.php` and `routes/console.php` did: merges `hata.*` (`HataConfig`), applies `SiteSettings`, registers routes, the `Route::localized()` macro, middleware (`SetLocale` on `web`, `LookUpContent` before `StartSession`), views, translations, Livewire and Blade namespaces, Flux overrides, migrations, commands, the schedule, the morph map, the admin menu and the asset directives. It registers `Hata\Providers\ContentServiceProvider` and `FortifyServiceProvider`.
- **Livewire SFC pages:** `resources/views/livewire/**/name.blade.php`, namespace `hata::` (`Livewire::addNamespace('hata', …)`), e.g. `hata::admin.users.index`. File names are plain ASCII, without Livewire's ⚡ prefix (Livewire finds both): macOS's `unzip` cannot extract UTF-8 names from the release archive, and Composer's fallback needs `php-zip`, which some hosts lack (`PackageFilesTest` guards it). Every full page declares its layout: `#[Layout('hata::layouts.app')]` (crop: `hata::layouts.focus`).
- **Full-page routes:** `Route::livewire('settings/profile', 'hata::settings.profile')->name(...)`. Layout `hata::layouts.app` → `resources/views/layouts/app/sidebar.blade.php`; every layout is also the component `<x-hata::layouts.…>` (`HataServiceProvider::LAYOUTS`).
- **Views and components:** views are `hata::…` (`hata::welcome`, `hata::site.entry`, `hata::partials.head`); anonymous components `<x-hata::confirm-modal>`, `<x-hata::admin.row-actions>` and the rest under `resources/views/components`. A site overrides a Blade view, component or layout in `resources/views/vendor/hata/…`; Livewire SFC pages cannot be overridden that way.
- **Page titles:** set with the `#[Title('...')]` attribute, which takes a literal string, so it can't be translated. Translated titles go through `render()`/`->title(__('...'))`; see the decisions below.
- **Auth views:** `resources/views/auth/*.blade.php` (`hata::auth.login` and so on; plain Blade, rendered by Fortify via `Hata\Providers\FortifyServiceProvider::configureViews`).
- **Settings:** `routes/settings.php` (profile, language, appearance, security), sub-navigation in `<x-hata::settings.layout>` (`resources/views/components/settings/layout.blade.php`).
- **Toasts:** `Flux::toast(...)` with `<flux:toast.group>` persisted in the sidebar layout.
- **Existing Actions:** `src/Actions/Fortify/*` (Fortify contracts, method names set by Fortify). `src/Concerns/*ValidationRules.php` are validation-rule traits.
- **The user model is the site's:** Hata resolves it with `Hata::userModel()` (from `auth.providers.users.model`) and never names `App\Models\User`; the model implements `Hata\Contracts\AdminUser` and uses `Hata\Models\Concerns\IsAdminUser` (written by `hata:install`); see `docs/specs/users.md`.
- **Host defaults:** `Date::use(CarbonImmutable::class)`, `DB::prohibitDestructiveCommands()` and `Password::defaults()` are the host's (its `AppServiceProvider`, written by `hata:install` from `stubs/app-service-provider-defaults.stub`), never Hata's; the suite runs without them (decision 71).
- **Assets:** `npm run build` writes `dist/` (`base: /vendor/hata/`, manifest `dist/.vite/manifest.json`); a site gets them in `public/vendor/hata` through the `hata-assets` publish in its `post-autoload-dump` (every `composer install`, update and dump-autoload; also under `laravel-assets` on `composer update`). Views print them with `@hataAssets`/`@hataFonts` (`Hata\Support\Assets\HataAssets`, its own `HataVite`); a module adds its own with `Hata\Support\Admin\AdminAssets::add()`. Commit `dist/` with every change to `resources/css` or `resources/js`; CI fails when it is stale.
- **Media batches:** `Hata\Actions\Media\MediaBatchEngine` (run state, lock, heartbeat, budgets, pause/resume/stop) is the base of `OptimizeExistingMedia` and `MoveMediaToDisk`; each has its queue job (`Hata\Jobs\MediaBatchJob` base), command (`Hata\Console\Commands\MediaBatchCommand` base: `media:optimize`, `media:move-disk {public|s3}`) and page (`Hata\Livewire\Admin\MediaBatchPage` base: `/admin/media/optimize`, `/admin/media/move`).
- **Scheduler:** `media:prune-deleted` and `content:prune-trash` run `daily()` (registered by `HataServiceProvider` on the host's `Schedule`); the first deletes the objects in `media_pending_deletions` when due: replaced objects on S3 and on the `public` disk, and their originals on `local`. Batches and the library page prune too, so no cron is required.
- **Media disks:** `config/hata.php` → `hata.media.disk` is `public` (rasters, static after `storage:link`) or `s3`; `local` stays private for originals, SVG and documents. `MEDIA_DISK=local` in `.env` is the private mode (everything through the app, no link, no move offered); saving the Media section stores `public` and ends it (decision 52, kept by decision 75). `Hata\Support\Media\MediaDisks` holds placement, `DirectServing` the link/probe state; see decision 52.
- **Cache locks:** media rebuilds, moves and batches use cache locks, so web, queue and CLI need one shared cache store (database, redis or file on one server), never `array`.
- **Migrations:** Hata's own load from `database/migrations` (`loadMigrationsFrom`); Laravel's users, cache and jobs tables are the host's. From the first release on, a shipped migration is never edited: a change is a new migration (decision 71).
- **Tests:** Pest on Orchestra Testbench (`Tests\TestCase`, `testbench.yaml`, `workbench/`), SQLite `:memory:` by default (phpunit.xml). Suites `Unit`, `Feature`, `AdminPath` (a custom admin path set before the routes load), `SeoRoutesOff` (sitemap and robots switched off before the routes load) and `Install` (no `RefreshDatabase`; the installer against host fixtures in `tests/fixtures/host`). `Tests\TestCase::call()` resets the scoped instances before every request, as separate requests would. `composer test` = pint --test + phpstan + pest. Run one database's suite at a time (SQLite, MySQL, PostgreSQL), and don't use `pest --parallel` (it crashes in Pest's Paratest wrapper). CI (`.github/workflows/tests.yml`): Pint and PHPStan, the `dist/` freshness check, and the suite on PHP 8.4/8.5 × SQLite/MySQL/PostgreSQL.
- **Translations** live in `resources/lang/en` and `resources/lang/uk` as `hata::` (PHP files; see Conventions).
- **Public site:** the home page (`HomeController`: the chosen page, the plain `hata::site.home-plain` where it is not public, or the Hata introduction `hata::site.home` while none is chosen, decision 79) and the content records at their addresses, both inside `Route::localized()`. Records are plain Blade (`ContentController`, `hata::layouts.site`, `hata::site.entry`, `site.list`, `site.term`, `partials/site/language-switcher.blade.php`), never Livewire, styled by their own small Vite entry `resources/css/site.css` (not the admin's `app.css`); see decision 59. The head is printed by `@hataHead` from the scoped `Hata\Support\Seo\PageMeta`; `/sitemap.xml` and `/robots.txt` are `SitemapController` and `RobotsController` (decisions 76–78).
- **Content:** the registry `Hata\Support\Content\ContentTypes` (`ContentType` classes: the kit's `PagesType`, `PostsType`, `CategoriesType`, `TagsType` in `src/Support/Content/Types`, a site's in its `app/ContentTypes`; listed in `config/hata.php` → `content.types` and registered by `ContentServiceProvider`; a new one is written into the site by `php artisan make:content-type`), the models `Entry`/`EntryGroup`/`EntryRedirect`, paths and slugs in `EntryPaths`, bodies through `BodySanitizer` (save) and `BodyRenderer` (render), save and trash actions in `Hata\Actions\Content`, the admin pages `hata::admin.content.*` (their logic in the classes `Hata\Livewire\Admin\EntryListPage`, `EntryFormPage` and `EntryEditPage`, the pages hold the markup), and the public side `LookUpContent`/`ContentRouter`/`ContentLookup`/`ContentMatch`/`ContentController`. Spec: `docs/specs/content.md`.
- **Admin menu:** `Hata\Support\Admin\AdminMenu` (groups and items, Hata's own sections register through it); spec `docs/specs/admin-menu.md`.
- **Admin extension points:** the registries `AdminMenu`, `AdminTopbar`, `DashboardWidgets` and `SettingsSections` extend `Hata\Support\Admin\Registry\Registry` (`add`, `remove`, `modify`, `has`, `find`; entries implement `Entry` and use `HasChanges`), are reached through `Hata\Admin::menu()`/`topbar()`/`dashboard()`/`settings()`/`assets()`, and Hata registers its own in an application `booting` callback. Targeted registries (`Hata\Support\Admin\Registry\TargetedRegistry`, `TargetScope`) hold the lists' columns, filters, row actions and bulk actions (`src/Support/Admin/Lists`) and the forms' cards (`src/Support/Admin/Forms`, `FormExtension`), reached through `Admin::columns()`/`filters()`/`rowActions()`/`bulkActions()`/`formCards()` with a target (`users`, `profile`, `register`, `content.*`, `content.@records`, `content.@taxonomies`, `content.<type key>`); the list pages use `Hata\Livewire\Admin\Concerns\HasListExtensions`, the forms `HasFormExtensions`, a list's tests `Hata\Testing\AssertsListQueries`, and a content type switches form parts off with `without()`. The site's `app/Providers/HataAdminServiceProvider.php` is written by `hata:install`; `hata:admin` lists what is registered; dashboard widgets extend `Hata\Livewire\Admin\Widget` (`make:dashboard-widget`). Spec `docs/specs/admin-extensions.md`.
- **Installer:** `php artisan hata:install` (`InstallCommand`, the host-file edits in `Hata\Support\Install\HostFiles`); see `docs/specs/package.md`.
- A local MySQL and PostgreSQL 18 are available via Herd (`mysql`, `psql`; user `root`, database `hata_testing`) for running the suite against them.

## Flux free vs Pro

Flux 2.21 free ships `table` (with `sortable` columns, `paginate`), `pagination`, `toast`, `modal`, `select` (native), `checkbox`, `badge`, `callout`, `dropdown`. Because `flux:table` is in the free package, we use it instead of a custom table component. Pro-only components (e.g. `flux:select variant="listbox"`, date pickers, `flux:autocomplete`) must not be used.

## Decisions

Each decision gives its date and its reason. Add new ones at the end.

1. **CLAUDE.md is committed.** It was removed from `.gitignore`; `AGENTS.md`, `.ai/` and `boost.json` stay local (generated by Boost).
2. **Email verification stays disabled** (no `Features::emailVerification()`, `User` doesn't implement `MustVerifyEmail`). The admin route group still carries the `verified` middleware, so it starts working once verification is enabled. The "email verified" checkbox only sets `email_verified_at`. Reason: shared hosting may not have working mail.
3. **The dashboard moves into the admin area:** `/admin`, route `admin.dashboard`, behind `can:admin.access`. `/settings/*` (profile, language, security, appearance) stays available to any authenticated user. After login (Fortify `home`), a user without `admin.access` is sent to `profile.edit` instead of a 403 page.
4. **Use `flux:table`** (it's in Flux free) instead of a custom Blade table component.
5. **Registration toggle:** `config/hata.php` → `hata.admin.registration_enabled` (env `ADMIN_REGISTRATION_ENABLED`, default `false`). `Features::registration()` is added to Fortify's features only when it's enabled. *Superseded by decision 37.*
6. **Page titles are translation keys.** `#[Title('settings.profile.title')]` holds a key, and `partials/head.blade.php` translates it with `__($title)`. A title passed already translated (`:title="__('...')"`) still works, because `__()` returns a missing key unchanged.
7. **Vendor literals without JSON files.** Fortify, laravel/passkeys and Flux call `__('Some English sentence')`. The project has no `lang/*.json`, so `Hata\Support\Translation\VendorTranslations` maps these literals to PHP keys (`auth.vendor.*`, `common.flux.*`) through `Lang::handleMissingKeysUsing()` in `HataServiceProvider`. When a package update adds a new literal, add it to that map and to both languages.
8. **Toast after a redirect:** `Hata\Support\Toast::success()/danger()` flashes to the session, and `<x-hata::flash-toast />` in the app layouts fires Flux's `toast-show` event on the next page. `Flux::toast()` stays for actions that don't redirect. This is the single toast approach for the whole admin.
9. **Language page:** `settings/language` (`language.edit`), a separate settings page. After saving, a full redirect (no `wire:navigate`) re-renders `<html lang>` in the new language. `User` implements `HasLocalePreference`, so emails such as password reset go out in the user's language.
10. **`welcome.blade.php` is not translated.** It's Laravel's demo landing page and will be replaced by the frontend themes stage. *Superseded by decision 79.*
11. **spatie/laravel-permission 8.4**, teams off, guard `web`. Spatie clears its own cache when roles or permissions change (`RefreshesPermissionCache`, `givePermissionTo`/`syncPermissions`), and `permissions:sync` clears it explicitly.
12. **Fortify `home` stays `/dashboard`.** That route (`dashboard`) only redirects: users with `admin.access` go to `admin.dashboard`, everyone else to `profile.edit`. This covers every Fortify flow (login, 2FA, passkeys, registration) without overriding Fortify response classes.
13. **DatabaseSeeder no longer creates "Test User".** (The seeder is now `Hata\Database\Seeders\HataSeeder`, called from the site's `DatabaseSeeder`, which `hata:install` writes.) That factory needs Faker (a dev dependency, missing after `composer install --no-dev`) and sets the password `password`. Instead the seeder runs `permissions:sync`, then `RoleSeeder`, then creates the super admin from `config('hata.admin.initial_admin')` (`ADMIN_NAME/EMAIL/PASSWORD`) if it doesn't exist yet. Running it repeatedly is safe.
14. **RoleSeeder only adds permissions** (defaults in `config/internal/permissions.php` → `roles`, `*` = all), so changes made by an administrator survive a reseed. The `admin` role picks up new permissions on every seed.
15. **`Hata\Enums\SystemRole`** holds the names of the system roles. `Hata\Models\Role::displayName()` returns `roles.names.<name>` for system roles and `label` for custom ones.
16. **`CreateSuperAdmin` is an action without an actor** (used by the CLI and the seeder). Actions with an actor (`CreateUser` and others) arrive in step 4.
17. **Artisan command output is in English.** It's for developers, not the admin UI.
18. **Starter registration tests are skipped** while registration is off (`skipUnlessFortifyHas`). *Superseded by decision 37: they now turn registration on in `beforeEach`.* `RegistrationToggleTest` covers that registration is off by default and that a new user gets no role.
19. **Laravel Boost appends its guidelines to this file** on `composer update/require` (the block at the end of the file, after the `===` line). Don't edit that block; Boost regenerates it. Never write the literal opening tag of that block anywhere else in this file: Boost would treat it as the block start and overwrite everything after it. *Since decision 72 Boost is installed in the demo app, not in this repository, so the block at the end of this file is no longer regenerated here; it stays as it is until it is removed on purpose.*
20. **Cyrillic-aware case-insensitive search:** the `users.search_index` column holds `mb_strtolower(name + ' ' + email)`, kept up to date by the `Hata\Models\Concerns\HasSearchIndex` trait (on `saving`). The `search()` scope does `LIKE` on the lowercased term. This works the same on SQLite (whose `LIKE` only ignores ASCII case) and MySQL, with no DB-specific SQL. `%`/`_` in the term are not escaped (they only widen the match). Reuse the trait for posts and pages.
21. **Protection rules** live in `Hata\Support\Permissions\AccessRules`, which actions call directly. Not via the Gate: `Gate::before` lets a super admin through everything, but the rules (self, last super admin) bind super admins too. The UI hides buttons using the same methods. A violation throws `Hata\Exceptions\ProtectedActionException` (an `AuthorizationException` with a translated message); components show it as a field error or a danger toast.
22. **Extra rule derived from rule 2:** only a super admin can edit or delete a super admin. Otherwise an admin could change a super admin's email or password and take over the account. The edit page returns 403 in that case.
23. **Rule 3 when removing a role** is checked before rule 2, so that an admin who tries to remove the role from the last super admin gets the "last super admin" message.
24. **Rule 5 for users** applies to roles being added; removing a role is limited only by rule 2. In the UI, roles you can't assign are disabled (with an explanation) both ways, and a disabled role that is already assigned stays assigned.
25. **Actions with an actor** call `Gate::forUser($actor)->authorize(...)` (users.create/edit/delete) and then the protection rules. `SyncUserRoles` doesn't check permissions itself; `CreateUser`/`UpdateUser` do it before calling it.
26. **When an admin edits a user**, changing the email doesn't reset `email_verified_at` (that's the admin's call; the "email verified" checkbox only exists on create).
27. **Shared UI pieces:** `<x-hata::confirm-modal>` (confirmation for destructive actions), `<x-hata::admin.empty-state>`, `<x-hata::admin.row-actions>` (per-row actions dropdown, see decision 35), and the partial `partials/admin/user-form.blade.php` for create/edit. Form object: `Hata\Livewire\Forms\UserForm`. Dates are shown with `isoFormat('LL')` (genitive case in Ukrainian).
28. **Roles:** the label of system roles is not edited (they're shown under their translated name `roles.names.*`); only their permissions change (rule 6). The technical name of a custom role is set only at creation (a slug from the label via `Str::slug`, transliterated, until it's edited by hand), and the format is `^[a-z0-9]+(-[a-z0-9]+)*$`.
29. **Rule 5 for roles** applies to permissions being added. In the matrix, permissions the actor lacks are disabled, and "select all / clear all" only touch the ones they can grant.
30. **Deleting a role:** the button is shown for custom roles. If the role has users, the dialog says how many and has no confirm button, and `DeleteRole` refuses anyway (rule 7).
31. **`roles.edit` without `roles.view`** also opens the role page (`RolePolicy::view`). With only `roles.view`, the page is in view mode.
32. **Base component `Hata\Livewire\Admin\RoleFormPage`** for the role create/edit pages (the matrix and select/clear by group). It's a class rather than a trait because PHPStan doesn't analyse SFC files and reports a trait used only inside them as unused.
33. **Minimum PHP 8.4** instead of 8.3 from the spec (user's decision, 2026-11-05). Pest 5 / PHPUnit 13 from the starter kit and Symfony 8 in the lock file require PHP 8.4+, so the project can't be installed on 8.3 without downgrading those dependencies.
34. **CI** (`.github/workflows/tests.yml`): a `quality` job (Pint `--test` and PHPStan, PHP 8.5) and a `tests` matrix (PHP 8.4/8.5 × SQLite in memory / MySQL 8 / PostgreSQL 18). Tests read the database from env variables; `phpunit.xml` sets SQLite only as the default (no `force`).
35. **Per-record actions in every table go into a "⋮" dropdown** (`<x-hata::admin.row-actions>` with `<flux:menu.item>` children, destructive ones `variant="danger"`), not into icon buttons in the row (user's decision, 2026-11-05). The component renders nothing when no item is visible to the actor. Page-level actions ("Create") stay as buttons above the table. The record's name in the first column links to its edit page when the actor may open it.

36. **Site settings override config** (2026-11-09). `Hata\Support\Settings\SiteSettings` stores values in the `settings` table and writes them over `config()` in `HataServiceProvider::boot()`, so code keeps reading config. No settings package (no new dependency). Settings that aren't stored fall back to `.env`. The SMTP password is encrypted with `APP_KEY`.
37. **Registration is switched at runtime.** Fortify always registers `Features::registration()`, because the setting lives in the database and Fortify builds its routes before that. `EnsureRegistrationIsEnabled` (in `fortify.middleware`) returns 404 on `register`/`register.store` while `hata.admin.registration_enabled` is off, and the "Sign up" links check the same config.
38. **The site timezone is for display only.** `app.timezone` stays UTC, so stored dates don't shift; admin views convert with `->tz(config('hata.admin.timezone'))`.
39. **Default logo and uploaded logos** (2026-11-09). *Uploads and the branding disk/route superseded by decision 49.* The default mark (`<x-hata::app-logo-icon>`, user picked variant 5 of 7: crossed rafters + four-pane window) replaces the starter kit logo and the Laravel favicon. Uploaded light/dark logos live on a private disk and are served by the `branding.logo` route with a versioned URL, so shared hosting needs no `storage:link`; SVG is allowed, protected by a CSP sandbox header. Layouts render `<x-hata::site-logo>`.
40. **Color schemes are CSS variables** (2026-11-09). A site-wide scheme (presets or one custom company color, user's decision) overrides `--color-zinc-*`, `--color-accent*` and `--color-sidebar*` with an inline style in `<head>` (`Hata\Support\ColorScheme\ColorScheme`), so no Tailwind rebuild. Shades are generated in OKLCH with contrast checks instead of storing palettes. New surfaces should use `bg-sidebar`/`border-sidebar-border` or zinc/accent utilities so schemes reach them.
41. **Media is served by a route, with ULID keys** (2026-11-10). Files live on a private disk (`config/hata.php` → `hata.media.disk`) and are served by a route that looks the file up by its ULID key, so no `storage:link` is needed on shared hosting and URLs can't be guessed or enumerated by id. *Superseded for raster images on this server by decision 52: they are now static files of the `public` disk; the route still serves SVG, documents and the fallback.* Responses carry `X-Content-Type-Options: nosniff`; SVG also gets a CSP sandbox header so an uploaded SVG can't run script. A request with the right key but an old name or extension redirects (301) to the current URL.
42. **Images go through Laravel's `Illuminate\Image`** (2026-11-10), which runs on `intervention/image` 4 (added with the user's approval). `HataServiceProvider::configureMedia()` sets `images.default` to `imagick` when the extension is loaded, else `gd`, because shared hosting often has GD only. App code talks only to the Laravel API. HEIC/AVIF need an Imagick build that supports them; the HEIC test skips without it.
43. **Resize twice, store as-is on failure** (2026-11-10). The browser shrinks images to 3840 px before upload (that file is the kept original), and the server then orients, scales to 2560 px and encodes WebP at quality 80. If the file is too big for `memory_limit` or can't be decoded, it is stored unchanged with `media.optimize_failure` (`too_large` / `unreadable`) instead of failing the upload or crashing the request. The details panel shows why it wasn't optimized.
44. **Deleting a folder deletes its contents, and every delete is confirmed** (2026-11-10). There is no trash, so each delete (file, bulk, folder) goes through `<x-hata::confirm-modal>`. A folder holding more than 10 files also requires typing its exact name, checked again on the server. Files in a deleted folder are removed with it, so the dialog states the count and how many are used somewhere.
45. **Media URLs carry `?v=`; only the current version is cached for a week** (2026-11-10). A crop or replace keeps the ULID key, so the URL alone can't get past browser caches. `Media::url()` and `thumbUrl()` add `?v={version}`, and the route sends `max-age=604800` only when `v` matches the current version; a stale or missing `v` gets `no-cache`. Old links keep working and stay fresh, and new links change as soon as the file does. Not `immutable`, so a wrong cache entry never sticks for long.
46. **One rebuild service for crop, replace and restore** (2026-11-10). `RebuildMediaFile` is the only code that rewrites a media file: it optimizes with the edits, writes the file, thumbnail and original, updates the row and bumps the version in one transaction, and puts the old bytes back if anything fails. Crop, replace and restore authorize and decide what to rebuild from, then call it, so the file rollback, the name/extension rules and the old-name redirect exist once instead of three times.
47. **Folders: collapsible tree, moves and per-folder menus** (2026-11-11, user's requests). The tree shows only the path to the open folder expanded (the rest is kept per browser in `localStorage`), caps its indent at depth 4 and gets a search over 15 folders, so deep or many folders stay readable. Folders move by drag or a "Move to…" folder picker (`MoveFolder`, in a locked transaction; never into itself or a descendant, and `descendantIds()` stops on a cycle). The open folder shows its subfolders as tiles, and every folder (tile, tree row, breadcrumb) has the same "⋮" menu from one partial. 50. **Media on S3-compatible storage** (2026-11-11). Cloud raster images and their thumbnails are served by direct CDN/bucket URLs with `?v={version}` when the disk has a public URL (else a 302 to a signed URL); SVG is always streamed through the app with the CSP sandbox and `nosniff`, never redirected to the bucket; documents and downloads go through the app route to a signed URL (valid for at least an hour) whose disposition carries the real file name. Cloud object paths carry the version (`{key}-v{version}`), so a rebuild never overwrites a committed object; replaced objects wait 7 days in `media_pending_deletions` (pruned by batches, the library page and a daily schedule, no worker or cron needed). Moving files between disks (`/admin/media/move`, `media:move-disk`) is a second mode of the optimize batch mechanism (`MediaBatchEngine` and its run/store/job/command/page bases), not a copy of it; a move bumps the version so `?v=` changes and a row moved back never reuses a path still pending deletion. Rebuilds and moves take a per-row cache lock (`RebuildMediaFile::lockName()`) plus a version guard, so the lock needs a cache store shared by web, queue and CLI (not `array`). SVG objects are written as `application/octet-stream` + `attachment`, so a direct bucket/CDN link can never render one on that origin. The `s3` disk keeps `'throw' => false`, so every media write and delete checks its result (a `false` write rolls the upload or rebuild back, a `false` delete is retried by the prune). A move insures each copy as a pending deletion due in a day and drops it on commit or cleanup, so a process killed mid-copy leaves nothing behind for long; its queue job's timeout is the batch lock (budget + 30 min). Signed URLs are signed from the start of the clock hour (valid 1 to 2 hours), so they stay the same within it.
51. **The media route runs without the `web` middleware group** (2026-11-12). `media.show` is declared with `->withoutMiddleware('web')`: on a local disk every image is a request to the app, and none needs a session, cookies, CSRF or `SetLocale`. Responses carry no cookies (so a proxy or CDN in front can cache them), and anything added to the route later must not rely on the session or the logged-in user.
52. **Local raster images are static files of the `public` disk** (2026-11-12). The default media disk is `public`: raster images and their thumbnails go there and the web server serves them (after `php artisan storage:link`); SVG, documents and every kept original stay on the private `local` disk, because only the app can add the sandbox, `nosniff` and download headers, and an original can carry EXIF data. Design: `docs/superpowers/specs/2026-11-12-media-direct-local-design.md`.

Reason: the user wanted descriptions, canonical and sharing tags without every theme re-implementing them.
77. **`/sitemap.xml` is built on request, with `Last-Modified`** (2026-11-24). No stored file and no job: the XML is streamed from cursors, per group of translations with `hreflang` alternates, and one query (the latest `updated_at`, the latest `published_at` that has come, the groups' `updated_at`, which linking and unlinking touch, and the `updated_at` of the settings that change the sitemap, never the media probe's, plus the stored-only marker `sitemap_changed_at` that `SiteSettings::put()` rewrites when one of them is stored or removed, since a removed row leaves no date) gives `Last-Modified` and the 304 that skips the build; the route runs without the `web` group (no session or cookies, cacheable by a proxy), is switched by `HATA_SITEMAP`, and a taxonomy has no list entry because the router has no list at a taxonomy base. Moving a page bumps its descendants' `updated_at` so `lastmod` follows. Known limit: one file, no split past 50,000 URLs. Reason: no cron or worker on shared hosting, and a crawler's repeated request costs one query.
78. **`/robots.txt` is a route, and the installer removes the stock file** (2026-11-24). Hata answers `User-agent: *` / `Disallow:` and the `Sitemap:` line when the sitemap is on (`HATA_ROBOTS` switches it off), never naming the admin path (the path may be hidden by `HATA_ADMIN_PATH`). The web server serves a file in `public/` before any route, so `hata:install` deletes Laravel's `public/robots.txt` only when it is exactly the stock text and never a changed one; sites installed before v0.3.0 delete it by hand (release notes, `docs/specs/package.md`). Reason: a route can name the sitemap's address, a static file cannot, and an edited file is the site's.
79. **The home page is a chosen record that follows its translations, with the Hata introduction or a plain home as the fallback** (2026-11-24, the user's choice; supersedes decision 10). The setting `home_page` stores a `pages` record id and the home is that record's current group in the visitor's language, so linking and unlinking translations changes no setting; trashing the record makes only its own language fall back (other public translations keep showing), and deleting it for good clears the setting in the same transaction (`DeleteEntry::purge()`). Two fallbacks (the final review's ruling): while no page is chosen at all, `hata::site.home` introduces Hata (full width, `noindex`, the homes left out of the sitemap, "Open the admin" for users with `admin.access` only, the documentation link for everyone); where a page is chosen but not public in the language, `hata::site.home-plain` shows the site name and the language's site description in the reading column, indexed and listed in the sitemap, so a live site never shows Hata's introduction to its visitors. Both carry a hint strip for `settings.edit`. The chosen page's own address and its translations' addresses answer 301 with `no-cache` to the home (a preview is not redirected; pages under it keep their addresses; `HomePage::includes()` takes the router's loaded group only as proof of a match and otherwise compares the group id through `HomePage::groupId()`, one query by primary key remembered for the request, only while a home page is chosen and only for a public `pages` record outside the home group), and the list and form mark it with a "Home page" badge. `hata::welcome` is removed: a site that overrode `vendor/hata/welcome.blade.php` loses it, a breaking change, released as v0.3.0. Reason: the user wanted the home page chosen in the admin, in every language, with no demo page left in the package.
80. **The last visited site language applies to guests only** (2026-11-24, the user's report: with the default interface language set to English, a signed-in admin without a language of their own still saw the admin in Ukrainian, because the session's last site language came before the default). Amends decision 56: a signed-in user gets `users.locale`, else `ContentLocales::interfaceDefault()`; only a guest gets the language of the site they last visited, as the field's help text says.
81. **Admin extension points share one registry base** (2026-11-25, release 1 of the user's request that everything visual in the admin be addable from a site or a module, and some of it hideable, without editing or overriding a Hata file, so `composer update` keeps bringing fixes; design `docs/superpowers/specs/2026-11-25-admin-extension-points-design.md`). `AdminMenu` and `SettingsSections` each re-implemented keys, order, permission and mistake handling, and more extension points would have copied that again with small differences, so `Hata\Support\Admin\Registry\Registry` holds it once and the menu, the settings sections, the new top bar (`AdminTopbar`) and the dashboard widgets (`DashboardWidgets`) are the same shape; `Hata\Admin` is the one entry point and the installer writes the site's `HataAdminServiceProvider` (never overwritten, examples commented out). Chosen over Blade slots (cannot sort, eager-load or be hidden by key, and bind a site to Hata's markup) and over replacing whole pages (the site stops receiving fixes). The calls: `remove()` hides a key for good in any call order, and to replace an entry a site adds one with the same key; `modify()` is applied at read, in call order; `modify()` and `remove()` of a key that is not there are skipped, never a mistake, because some entries exist only at read time (a content type switched off, a lazy provider), and `hata:admin` lists them as unmatched; Hata registers its own entries in a `booting` callback so they exist before any provider's `boot()`; keys are lowercase letters and digits joined by hyphens or dots, with menu items also allowing underscores (content type keys are `[a-z0-9_-]+`) and settings sections hyphens only (they are `?tab=` values); menu route checks run for every item, not only the visible ones, so a mistake shows to the developer whoever is signed in. The top bar is desktop-only (a phone would lose a header row) with plain links, and "View site" stays in the sidebar on mobile. The `content` and `administration` groups are collapsible, drawn with Hata's own markup so they look like the other groups (Flux's expandable group looked different and left a gap when folded), the state kept per browser in `localStorage` (`hata.menu.collapsed`) and applied by an inline script before paint, the group holding the current page always open. The dashboard is lazy widgets in one bundled request (`lazy.bundle`) in a `md:grid-cols-6` grid; a widget's error card covers failures in `body()`, not a Blade error in its view, `title()` must stay cheap because the placeholder calls it, and the widget's permission is checked when the dashboard lists it. Hata's widgets are `content` (full, 10: a tile per type) and `recent-changes` (full, 20), one query on `entries` each, both full width because the tiles and rows needed it (the user's browser pass); a widget may give an `icon()`; recent changes has no author column, which is what keeps it to one query, and "published" counts the stored status, so a scheduled record counts as published. Released as v0.4.0 (minor: the dashboard changes and "View site" moves); release 2 (list columns, filters, row and bulk actions, form cards, content type fields) follows as v0.5.0.
82. **The suite runs on PostgreSQL too** (2026-11-25, the user's request). CI's matrix is PHP 8.4/8.5 × SQLite / MySQL 8 / PostgreSQL 18. Two things PostgreSQL needed: a descendant's new path in `EntryPaths::move()` is built with `||` on SQLite and PostgreSQL and `CONCAT()` only on MySQL and MariaDB (PostgreSQL cannot type a bare parameter inside `CONCAT()`), and a statement that may fail on purpose inside a transaction runs in its own `DB::transaction()` (a savepoint when nested), because PostgreSQL aborts the whole transaction on a failed statement (`RunMaintenanceAction` claiming the run slot; tests that expect a unique violation). New raw SQL is checked on all three databases.
83. **Admin extension points, release 2: lists and forms are extended through targeted registries** (2026-11-26, the user's request that columns, filters, actions and form fields be addable from a site or a module without editing or overriding a Hata file; design `docs/superpowers/specs/2026-11-25-admin-extension-points-design.md`). Five registries (`TableColumns`, `TableFilters`, `RowActions`, `BulkActions`, `FormCards`) share `TargetedRegistry`: `Admin::columns('content.posts')->add(...)` is recorded per target and resolved when a list or form opens, replaying the chain `content.*`, then `content.@records` or `content.@taxonomies`, then the type, adds first, then modifications, then removals, so a narrower target overrides or hides an entry for itself only and provider order never matters. Chosen over a hook per page (it would not compose, hide or reorder) and over replacing the views (the site stops receiving fixes). Calls made: Hata's own columns of the users and content lists are registry entries, so a site reorders or hides them, but the first column and the "⋮" column are fixed, and Hata's own row actions, bulk actions and form blocks are not entries (a site adds, never replaces them); key alphabets differ per registry because the keys are used differently (columns are `?sortBy=` values and allow underscores; filters, actions and cards are Livewire paths or `wire:click` arguments and allow hyphens and underscores, no dots); a column, filter or action costs at most one query per page, never one per row, asserted with `Hata\Testing\AssertsListQueries`; no sorting by keys of the JSON `fields` column (decision 57); a registered sort flattens the content list's tree and tab counts ignore registered filters; a registered filter counts only while it is visible and holds one of its options (one predicate for applying it, the filtered state and the tree indent, which goes flat with it); row and bulk actions are not shown in the trash unless their `visibleIn` says so, and their handlers load records only through the list's scoped query (an id outside the view is 404 for a row action and dropped from a bulk action, a refused record 403), which is the security boundary, while the confirm step is only a UI step; before a registered action runs the list re-authorizes what its `mount()` checks (`authorizeList()`), and a handler refuses by throwing `ProtectedActionException` (or a `ValidationException`), shown as a danger toast like Hata's own refusals; a row action's permission is checked per record and must not query, a bulk action's once for the actor, and on the users list a bulk handler gets whoever was selected, so it applies `AccessRules` itself. A permission closure of a list or form entry gets the `ListContext` or `FormContext` as its last argument (a row action's the record before it), and the list entries take their tail in one order (`visibleIn`, `permission`, `order`, then their own options), best given as named arguments. A form card is part of the form, not a component of its own: its values are validated together with the form (any error stops the save) and saved inside the form's transaction after the record and before any redirect, and whatever its `save()` throws rolls the record back (`FormCardFailed` keeps an action's own catches from taking it for the record's error; a `ValidationException` is shown under the card, anything else surfaces as it was); only the top-level keys a card's `rules()` names reach `save()`, validation belongs in `rules()`, and the card's view binds with `<flux:input :attributes="$field('name')" />` because Blade cannot spread `{{ $field(...) }}` inside a component tag. One card view serves the user form, the profile page and registration (bare on the last two); those three forms have one column and draw the `side` cards after the `main` ones, and on registration the old input is the cards' `$values`, so a select or a checkbox is marked from it; a card's permission for a guest is only a Closure. Recorded deviation from the design: `AssertsFormQueries` (design section 9) was not built (the plan dropped it): a card's `fill()` cost is the site's, and the docs ask for one query at most. A content type switches parts of its form off with `without()` (`body`, `image`, `publication`, `author`, `excerpt`, `seo`), `supports()` answers `excerpt` and `seo` too, and a switched-off part keeps its stored value and is off on the public pages too (no image, body or share image of a type without them), while a new record always gets its creator as `author_id`. Breaking, small: a type subclass that overrides `supports()` should move to `without()`, and `data-test="term-records-*"` moved from the cell to an inner span; a site that overrode nothing is unaffected. `hata:admin` prints a table per target; the provider stub carries a commented example of each point. Released as v0.5.0.
84. **A content type's fields are searched through the search index, not through query rules** (2026-11-26, the user's request: "search by some field of a content type"; they chose this of three options). `Field::searchable()` puts a field's value into the record's `search_index` on save, next to the title and the slug, and a type adds the excerpt with a protected `searchable()` returning `['excerpt']`. Chosen over a registry of search rules (closures adding conditions to the list's query): the search stays one `LIKE` on one column whatever a type adds, behaves the same on the three databases with Cyrillic case folding done once in PHP (decision 20), and the JSON `fields` column is still never queried (decision 57). The price is that the index is written on save: `content:reindex-search` rebuilds it for records stored before a field became searchable, a shared field refreshes the index of every translation (also when a record is linked into another group), and both write only the column, never `updated_at`. The body is not indexed (size). Search rules for a module's own table are left until a module needs them; a maintenance-page button for the reindex is not built yet.

## Conventions

- **Translations:** PHP files only in `resources/lang/{en,uk}`, loaded as the `hata::` namespace (`__('hata::users.title')`; a site overrides a line in `lang/vendor/hata/`). Laravel's own groups (`validation`, `passwords`, `pagination`, `auth.failed|password|throttle`) are global and live in `resources/lang-framework`. A content type's labels come from `translationPrefix()` (`''` for a site's type, `hata::` for the kit's) and a permission group's from the prefix it was registered with (`PermissionRegistry::register($group, $actions, 'shop::permissions')`). Keys are snake_case and nested by page/block. Every new key goes into both languages in the same change. `tests/Feature/Localization/TranslationParityTest.php` checks file/key parity, empty values and placeholders (also for `resources/lang-framework`, against Laravel's own English), that every `__('hata::group.key')` used in `src/` and `resources/views/` exists, that none is used without `hata::`, and that every vendor-map target exists.
- **Languages:** interface languages are `config('hata.admin.interface_locales')`; the `SetLocale` middleware (web group) applies, for a signed-in user, `users.locale` else the site's default, and for a guest the last visited site language else the site's default (`ContentLocales::interfaceDefault()`, not `config('app.locale')`). Content languages are `Hata\Support\Localization\ContentLocales`; public routes go inside `Route::localized()` and build their addresses with `ContentLocales::route()`.
- **Permissions:** declared in Hata's internal `config/internal/permissions.php` (`hata.permissions.groups`, not published), so a site or module adds its own groups only through `PermissionRegistry::register()`, never through config. Run `php artisan permissions:sync` (`--prune` deletes stale ones). Labels are `permissions.groups.*`/`permissions.items.*` in the registering owner's translations (`hata::permissions` for Hata's own and the kit types, the site's `permissions` by default, `shop::permissions` via the third argument of `register()`; `groupLabel()`/`permissionLabel()` fall back to the site's `permissions.*`); a test checks that every permission has a translation. Code checks permissions (`can('users.edit')`), never role names; the only exception is super-admin in `Gate::before`.
- **Admin routes:** `routes/admin.php`, prefix `config('hata.admin.path')` (`HATA_ADMIN_PATH`, default `admin`; one segment, validated by `Hata\Support\Admin\AdminPath` while the routes register; `/admin` in the specs and decisions means this path), names `admin.*`, middleware `auth, verified, can:admin.access`.
- **Tests:** `seedRolesAndPermissions()` (tests/Pest.php), and the factory states `User::factory()->withRole('editor')` and `->withPermissions([...])` (the workbench's `App\Models\User`, which plays the site's model). `Tests\TestCase` pins the content types to pages (decision 68).
- **Host code:** Hata never names the site's classes (`App\Models\User`, `App\…`); it reads them from config (`Hata::userModel()`) or receives them through its registries. A host file is changed only by `hata:install` or `make:content-type`, by its skeleton shape, and is left untouched with printed by-hand lines when it does not match.
