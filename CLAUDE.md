## Starter kit structure

- **Livewire SFC pages:** `resources/views/pages/**/⚡name.blade.php`, namespace `pages::` (Livewire's default `component_namespaces`, config not published). The ⚡ emoji prefix is on.
- **Full-page routes:** `Route::livewire('settings/profile', 'pages::settings.profile')->name(...)`. Layout: `layouts::app` → `resources/views/layouts/app/sidebar.blade.php`.
- **Page titles:** set with the `#[Title('...')]` attribute, which takes a literal string, so it can't be translated. Translated titles go through `render()`/`->title(__('...'))`; see the decisions below.
- **Auth views:** `resources/views/pages/auth/*.blade.php` (plain Blade, rendered by Fortify via `FortifyServiceProvider::configureViews`).
- **Settings:** `routes/settings.php` (profile, appearance, security), sub-navigation in `pages/settings/layout.blade.php`.
- **Toasts:** `Flux::toast(...)` with `<flux:toast.group>` persisted in the sidebar layout.
- **Existing Actions:** `app/Actions/Fortify/*` (Fortify contracts, method names set by Fortify). `app/Concerns/*ValidationRules.php` are validation-rule traits.
- **AppServiceProvider:** `Date::use(CarbonImmutable::class)`, `DB::prohibitDestructiveCommands()` in production, `Password::defaults()` (strict in production, `null` otherwise).
- **Media batches:** `App\Actions\Media\MediaBatchEngine` (run state, lock, heartbeat, budgets, pause/resume/stop) is the base of `OptimizeExistingMedia` and `MoveMediaToDisk`; each has its queue job (`App\Jobs\MediaBatchJob` base), command (`App\Console\Commands\MediaBatchCommand` base: `media:optimize`, `media:move-disk {public|s3}`) and page (`App\Livewire\Admin\MediaBatchPage` base: `/admin/media/optimize`, `/admin/media/move`).
- **Scheduler:** `media:prune-deleted` runs `daily()` (`routes/console.php`); it deletes the objects in `media_pending_deletions` when due: replaced objects on S3 and on the `public` disk, and their originals on `local`. Batches and the library page prune too, so no cron is required.
- **Media disks:** `config/media.php` → `disk` is `public` (rasters, static after `storage:link`) or `s3`; `local` stays private for originals, SVG and documents. `MEDIA_DISK=local` in `.env` is the private mode (everything through the app, no link, no move offered); saving the Media tab with "This server" stores `public` and ends it. `App\Support\Media\MediaDisks` holds placement, `DirectServing` the link/probe state; see decision 52.
- **Cache locks:** media rebuilds, moves and batches use cache locks, so web, queue and CLI need one shared cache store (database, redis or file on one server), never `array`.
- **Tests:** Pest, SQLite `:memory:` (phpunit.xml), `RefreshDatabase` for Feature tests. `composer test` = pint --test + phpstan + tests. CI (`.github/workflows/tests.yml`) runs `composer setup` + `composer ci:check`.
- **No `lang/` directory** before stage 1. About 106 unique `__('Literal')` strings in the starter kit.
- `.ai/` contains only `mcp/mcp.json`; there is no `.ai/rules`.
- A local MySQL is available via Herd (`mysql` binary) for running the suite against MySQL.

## Flux free vs Pro

Flux 2.21 free ships `table` (with `sortable` columns, `paginate`), `pagination`, `toast`, `modal`, `select` (native), `checkbox`, `badge`, `callout`, `dropdown`. Because `flux:table` is in the free package, we use it instead of a custom table component. Pro-only components (e.g. `flux:select variant="listbox"`, date pickers, `flux:autocomplete`) must not be used.

## Decisions

Each decision gives its date and its reason. Add new ones at the end.

1. **CLAUDE.md is committed.** It was removed from `.gitignore`; `AGENTS.md`, `.ai/` and `boost.json` stay local (generated by Boost).
2. **Email verification stays disabled** (no `Features::emailVerification()`, `User` doesn't implement `MustVerifyEmail`). The admin route group still carries the `verified` middleware, so it starts working once verification is enabled. The "email verified" checkbox only sets `email_verified_at`. Reason: shared hosting may not have working mail.
3. **The dashboard moves into the admin area:** `/admin`, route `admin.dashboard`, behind `can:admin.access`. `/settings/*` (profile, language, security, appearance) stays available to any authenticated user. After login (Fortify `home`), a user without `admin.access` is sent to `profile.edit` instead of a 403 page.
4. **Use `flux:table`** (it's in Flux free) instead of a custom Blade table component.
5. **Registration toggle:** `config/admin.php` → `registration_enabled` (env `ADMIN_REGISTRATION_ENABLED`, default `false`). `Features::registration()` is added to Fortify's features only when it's enabled. *Superseded by decision 37.*
6. **Page titles are translation keys.** `#[Title('settings.profile.title')]` holds a key, and `partials/head.blade.php` translates it with `__($title)`. A title passed already translated (`:title="__('...')"`) still works, because `__()` returns a missing key unchanged.
7. **Vendor literals without JSON files.** Fortify, laravel/passkeys and Flux call `__('Some English sentence')`. The project has no `lang/*.json`, so `App\Support\Translation\VendorTranslations` maps these literals to PHP keys (`auth.vendor.*`, `common.flux.*`) through `Lang::handleMissingKeysUsing()` in `AppServiceProvider`. When a package update adds a new literal, add it to that map and to both languages.
8. **Toast after a redirect:** `App\Support\Toast::success()/danger()` flashes to the session, and `<x-flash-toast />` in the app layouts fires Flux's `toast-show` event on the next page. `Flux::toast()` stays for actions that don't redirect. This is the single toast approach for the whole admin.
9. **Language page:** `settings/language` (`language.edit`), a separate settings page. After saving, a full redirect (no `wire:navigate`) re-renders `<html lang>` in the new language. `User` implements `HasLocalePreference`, so emails such as password reset go out in the user's language.
10. **`welcome.blade.php` is not translated.** It's Laravel's demo landing page and will be replaced by the frontend themes stage.
11. **spatie/laravel-permission 8.4**, teams off, guard `web`. Spatie clears its own cache when roles or permissions change (`RefreshesPermissionCache`, `givePermissionTo`/`syncPermissions`), and `permissions:sync` clears it explicitly.
12. **Fortify `home` stays `/dashboard`.** That route (`dashboard`) only redirects: users with `admin.access` go to `admin.dashboard`, everyone else to `profile.edit`. This covers every Fortify flow (login, 2FA, passkeys, registration) without overriding Fortify response classes.
13. **DatabaseSeeder no longer creates "Test User".** That factory needs Faker (a dev dependency, missing after `composer install --no-dev`) and sets the password `password`. Instead the seeder runs `permissions:sync`, then `RoleSeeder`, then creates the super admin from `config('admin.initial_admin')` (`ADMIN_NAME/EMAIL/PASSWORD`) if it doesn't exist yet. Running it repeatedly is safe.
14. **RoleSeeder only adds permissions** (defaults in `config/permissions.php` → `roles`, `*` = all), so changes made by an administrator survive a reseed. The `admin` role picks up new permissions on every seed.
15. **`App\Enums\SystemRole`** holds the names of the system roles. `App\Models\Role::displayName()` returns `roles.names.<name>` for system roles and `label` for custom ones.
16. **`CreateSuperAdmin` is an action without an actor** (used by the CLI and the seeder). Actions with an actor (`CreateUser` and others) arrive in step 4.
17. **Artisan command output is in English.** It's for developers, not the admin UI.
18. **Starter registration tests are skipped** while registration is off (`skipUnlessFortifyHas`). *Superseded by decision 37: they now turn registration on in `beforeEach`.* `RegistrationToggleTest` covers that registration is off by default and that a new user gets no role.
19. **Laravel Boost appends its guidelines to this file** on `composer update/require` (the block at the end of the file, after the `===` line). Don't edit that block; Boost regenerates it. Never write the literal opening tag of that block anywhere else in this file: Boost would treat it as the block start and overwrite everything after it.
20. **Cyrillic-aware case-insensitive search:** the `users.search_index` column holds `mb_strtolower(name + ' ' + email)`, kept up to date by the `App\Models\Concerns\HasSearchIndex` trait (on `saving`). The `search()` scope does `LIKE` on the lowercased term. This works the same on SQLite (whose `LIKE` only ignores ASCII case) and MySQL, with no DB-specific SQL. `%`/`_` in the term are not escaped (they only widen the match). Reuse the trait for posts and pages.
21. **Protection rules** live in `App\Support\Permissions\AccessRules`, which actions call directly. Not via the Gate: `Gate::before` lets a super admin through everything, but the rules (self, last super admin) bind super admins too. The UI hides buttons using the same methods. A violation throws `App\Exceptions\ProtectedActionException` (an `AuthorizationException` with a translated message); components show it as a field error or a danger toast.
22. **Extra rule derived from rule 2:** only a super admin can edit or delete a super admin. Otherwise an admin could change a super admin's email or password and take over the account. The edit page returns 403 in that case.
23. **Rule 3 when removing a role** is checked before rule 2, so that an admin who tries to remove the role from the last super admin gets the "last super admin" message.
24. **Rule 5 for users** applies to roles being added; removing a role is limited only by rule 2. In the UI, roles you can't assign are disabled (with an explanation) both ways, and a disabled role that is already assigned stays assigned.
25. **Actions with an actor** call `Gate::forUser($actor)->authorize(...)` (users.create/edit/delete) and then the protection rules. `SyncUserRoles` doesn't check permissions itself; `CreateUser`/`UpdateUser` do it before calling it.
26. **When an admin edits a user**, changing the email doesn't reset `email_verified_at` (that's the admin's call; the "email verified" checkbox only exists on create).
27. **Shared UI pieces:** `<x-confirm-modal>` (confirmation for destructive actions), `<x-admin.empty-state>`, `<x-admin.row-actions>` (per-row actions dropdown, see decision 35), and the partial `partials/admin/user-form.blade.php` for create/edit. Form object: `App\Livewire\Forms\UserForm`. Dates are shown with `isoFormat('LL')` (genitive case in Ukrainian).
28. **Roles:** the label of system roles is not edited (they're shown under their translated name `roles.names.*`); only their permissions change (rule 6). The technical name of a custom role is set only at creation (a slug from the label via `Str::slug`, transliterated, until it's edited by hand), and the format is `^[a-z0-9]+(-[a-z0-9]+)*$`.
29. **Rule 5 for roles** applies to permissions being added. In the matrix, permissions the actor lacks are disabled, and "select all / clear all" only touch the ones they can grant.
30. **Deleting a role:** the button is shown for custom roles. If the role has users, the dialog says how many and has no confirm button, and `DeleteRole` refuses anyway (rule 7).
31. **`roles.edit` without `roles.view`** also opens the role page (`RolePolicy::view`). With only `roles.view`, the page is in view mode.
32. **Base component `App\Livewire\Admin\RoleFormPage`** for the role create/edit pages (the matrix and select/clear by group). It's a class rather than a trait because PHPStan doesn't analyse SFC files and reports a trait used only inside them as unused.
33. **Minimum PHP 8.4** instead of 8.3 from the spec (user's decision, 2026-11-05). Pest 5 / PHPUnit 13 from the starter kit and Symfony 8 in the lock file require PHP 8.4+, so the project can't be installed on 8.3 without downgrading those dependencies.
34. **CI** (`.github/workflows/tests.yml`): a `quality` job (Pint `--test` and PHPStan, PHP 8.5) and a `tests` matrix (PHP 8.4/8.5 × SQLite in memory / MySQL 8). Tests read the database from env variables; `phpunit.xml` sets SQLite only as the default (no `force`).
35. **Per-record actions in every table go into a "⋮" dropdown** (`<x-admin.row-actions>` with `<flux:menu.item>` children, destructive ones `variant="danger"`), not into icon buttons in the row (user's decision, 2026-11-05). The component renders nothing when no item is visible to the actor. Page-level actions ("Create") stay as buttons above the table. The record's name in the first column links to its edit page when the actor may open it.

36. **Site settings override config** (2026-11-09). `App\Support\Settings\SiteSettings` stores values in the `settings` table and writes them over `config()` in `AppServiceProvider::boot()`, so code keeps reading config. No settings package (no new dependency). Settings that aren't stored fall back to `.env`. The SMTP password is encrypted with `APP_KEY`.
37. **Registration is switched at runtime.** Fortify always registers `Features::registration()`, because the setting lives in the database and Fortify builds its routes before that. `EnsureRegistrationIsEnabled` (in `fortify.middleware`) returns 404 on `register`/`register.store` while `admin.registration_enabled` is off, and the "Sign up" links check the same config.
38. **The site timezone is for display only.** `app.timezone` stays UTC, so stored dates don't shift; admin views convert with `->tz(config('admin.timezone'))`.
39. **Default logo and uploaded logos** (2026-11-09). *Uploads and the branding disk/route superseded by decision 49.* The default mark (`<x-app-logo-icon>`, user picked variant 5 of 7: crossed rafters + four-pane window) replaces the starter kit logo and the Laravel favicon. Uploaded light/dark logos live on a private disk and are served by the `branding.logo` route with a versioned URL, so shared hosting needs no `storage:link`; SVG is allowed, protected by a CSP sandbox header. Layouts render `<x-site-logo>`.
40. **Color schemes are CSS variables** (2026-11-09). A site-wide scheme (presets or one custom company color, user's decision) overrides `--color-zinc-*`, `--color-accent*` and `--color-sidebar*` with an inline style in `<head>` (`App\Support\ColorScheme\ColorScheme`), so no Tailwind rebuild. Shades are generated in OKLCH with contrast checks instead of storing palettes. New surfaces should use `bg-sidebar`/`border-sidebar-border` or zinc/accent utilities so schemes reach them.
41. **Media is served by a route, with ULID keys** (2026-11-10). Files live on a private disk (`config/media.php` → `disk`) and are served by a route that looks the file up by its ULID key, so no `storage:link` is needed on shared hosting and URLs can't be guessed or enumerated by id. *Superseded for raster images on this server by decision 52: they are now static files of the `public` disk; the route still serves SVG, documents and the fallback.* Responses carry `X-Content-Type-Options: nosniff`; SVG also gets a CSP sandbox header so an uploaded SVG can't run script. A request with the right key but an old name or extension redirects (301) to the current URL.
42. **Images go through Laravel's `Illuminate\Image`** (2026-11-10), which runs on `intervention/image` 4 (added with the user's approval). `AppServiceProvider::configureMedia()` sets `images.default` to `imagick` when the extension is loaded, else `gd`, because shared hosting often has GD only. App code talks only to the Laravel API. HEIC/AVIF need an Imagick build that supports them; the HEIC test skips without it.
43. **Resize twice, store as-is on failure** (2026-11-10). The browser shrinks images to 3840 px before upload (that file is the kept original), and the server then orients, scales to 2560 px and encodes WebP at quality 80. If the file is too big for `memory_limit` or can't be decoded, it is stored unchanged with `media.optimize_failure` (`too_large` / `unreadable`) instead of failing the upload or crashing the request. The details panel shows why it wasn't optimized.
44. **Deleting a folder deletes its contents, and every delete is confirmed** (2026-11-10). There is no trash, so each delete (file, bulk, folder) goes through `<x-confirm-modal>`. A folder holding more than 10 files also requires typing its exact name, checked again on the server. Files in a deleted folder are removed with it, so the dialog states the count and how many are used somewhere.
45. **Media URLs carry `?v=`; only the current version is cached for a week** (2026-11-10). A crop or replace keeps the ULID key, so the URL alone can't get past browser caches. `Media::url()` and `thumbUrl()` add `?v={version}`, and the route sends `max-age=604800` only when `v` matches the current version; a stale or missing `v` gets `no-cache`. Old links keep working and stay fresh, and new links change as soon as the file does. Not `immutable`, so a wrong cache entry never sticks for long.
46. **One rebuild service for crop, replace and restore** (2026-11-10). `RebuildMediaFile` is the only code that rewrites a media file: it optimizes with the edits, writes the file, thumbnail and original, updates the row and bumps the version in one transaction, and puts the old bytes back if anything fails. Crop, replace and restore authorize and decide what to rebuild from, then call it, so the file rollback, the name/extension rules and the old-name redirect exist once instead of three times.
47. **Folders: collapsible tree, moves and per-folder menus** (2026-11-11, user's requests). The tree shows only the path to the open folder expanded (the rest is kept per browser in `localStorage`), caps its indent at depth 4 and gets a search over 15 folders, so deep or many folders stay readable. Folders move by drag or a "Move to…" folder picker (`MoveFolder`, in a locked transaction; never into itself or a descendant, and `descendantIds()` stops on a cycle). The open folder shows its subfolders as tiles, and every folder (tile, tree row, breadcrumb) has the same "⋮" menu from one partial. The details panel closes when its file leaves the view; while anything is selected, a plain tile click toggles the pick.
48. **Media optimization picks its driver itself, and queued jobs re-apply the site settings** (2026-11-11). "Optimize existing files" runs on the queue when `queue.default` isn't `sync` (a self-chaining `OptimizeExistingMediaBatch`), else the open page processes batches; with a queue, the page falls back to processing after 30 s without a heartbeat while no batch holds the lock. `Queue::before` in `AppServiceProvider` re-applies `SiteSettings` before every job (and `media:optimize` before every batch), because the settings live in the database and a worker boots once. It skips jobs on the `sync` connection: they run inside a request that already applied the settings, and re-applying would put the site default back into `app.locale` after `SetLocale`.
49. **Logos are library files** (2026-11-11). The light and dark logos are ordinary media files chosen with the media picker, so there is no logo upload, `branding` disk or `branding.logo` route any more. `logo_light`/`logo_dark` hold media ids (cast to int into `admin.logo.*`), and each choice is recorded in `media_usages` against the `Setting` row, which implements `UsesMedia`: the library shows "Site logo (light/dark)" in the file's details, and deleting the file (or its folder) clears the setting inside the delete's transaction (config and cache refresh only after commit). Logos uploaded before this change are imported into the library by the migration `import_branding_logos_into_media` (a top-level "Logo" folder, `UploadMedia::import()` without an actor like decision 16; a logo that can't be imported is dropped, the deploy never fails).
50. **Media on S3-compatible storage** (2026-11-11). Cloud raster images and their thumbnails are served by direct CDN/bucket URLs with `?v={version}` when the disk has a public URL (else a 302 to a signed URL); SVG is always streamed through the app with the CSP sandbox and `nosniff`, never redirected to the bucket; documents and downloads go through the app route to a signed URL (valid for at least an hour) whose disposition carries the real file name. Cloud object paths carry the version (`{key}-v{version}`), so a rebuild never overwrites a committed object; replaced objects wait 7 days in `media_pending_deletions` (pruned by batches, the library page and a daily schedule, no worker or cron needed). Moving files between disks (`/admin/media/move`, `media:move-disk`) is a second mode of the optimize batch mechanism (`MediaBatchEngine` and its run/store/job/command/page bases), not a copy of it; a move bumps the version so `?v=` changes and a row moved back never reuses a path still pending deletion. Rebuilds and moves take a per-row cache lock (`RebuildMediaFile::lockName()`) plus a version guard, so the lock needs a cache store shared by web, queue and CLI (not `array`). SVG objects are written as `application/octet-stream` + `attachment`, so a direct bucket/CDN link can never render one on that origin. The `s3` disk keeps `'throw' => false`, so every media write and delete checks its result (a `false` write rolls the upload or rebuild back, a `false` delete is retried by the prune). A move insures each copy as a pending deletion due in a day and drops it on commit or cleanup, so a process killed mid-copy leaves nothing behind for long; its queue job's timeout is the batch lock (budget + 30 min). Signed URLs are signed from the start of the clock hour (valid 1 to 2 hours), so they stay the same within it.
51. **The media route runs without the `web` middleware group** (2026-11-12). `media.show` is declared with `->withoutMiddleware('web')`: on a local disk every image is a request to the app, and none needs a session, cookies, CSRF or `SetLocale`. Responses carry no cookies (so a proxy or CDN in front can cache them), and anything added to the route later must not rely on the session or the logged-in user.
52. **Local raster images are static files of the `public` disk** (2026-11-12). The default media disk is `public`: raster images and their thumbnails go there and the web server serves them (after `php artisan storage:link`); SVG, documents and every kept original stay on the private `local` disk, because only the app can add the sandbox, `nosniff` and download headers, and an original can carry EXIF data. Placement is one rule (`MediaDisks::diskFor`/`originalsDisk`; `publishes()` is decided by the disk's identity, `public` with a local driver, never by its URL) used by upload and by the disk move, and the `public` disk versions its paths and defers deletes like S3, so a week of caching never shows a stale file. Static URLs are handed out only when the link exists and a browser probe (the admin layout, for users with `settings.edit`) loaded the probe image `media/probe.png` (random size, checked with `new Image()` like a real `<img>`, so no CORS or dotfile rule can differ) from the current public URL; a failed or unreported probe is retried after 30 minutes, a confirmed one rechecked after 24 hours, and the results are stored-only settings written without re-applying config. Otherwise images go through `media.show`, and `media.static` (`/storage/media/{path}`) answers static addresses without the link (one query by the key in the file name; an older version 302s to the current file). `media.show` stays the permanent address and 302-redirects rasters to the static URL. `MEDIA_DISK=local` stays supported from `.env` as a private mode (everything through the app, no link needed, no move offered); the Media tab can't select it, and saving the tab with "This server" stores `public` and ends it. The user wanted no extra PHP load for images, working out of the box, and no broken image when the link is missing. Web server caching: `public/.htaccess` and the nginx snippet in the README. Design: `docs/superpowers/specs/2026-11-12-media-direct-local-design.md`.
53. **The media library renders in islands, narrowing is an explicit flag, and nothing inside an island uses a `wire:` action** (2026-11-12, performance review at the user's request: "everything must work fast and smoothly"). The library page has the islands `bulk`, `files` (the grid or the list) and `details` (`always: true`). The hot actions (tile or row click, pick, mouse box, checkboxes, "Show more", sort, closing the panel) take a trailing `$narrow` flag from the browser and then render only the islands they change (`renderOnly()`), skipping the folder tree, counters and months; any other action, or a request with a second call or a property update, renders the whole page. Livewire's own island behavior must never kick in on this page: it renders only the island an action started in (leaving dialogs, the tree and counters stale) and sends such actions in parallel with the page's other requests, each answering with the whole state, so a click during an upload could undo the upload's state. It is triggered by `wire:click`/`wire:submit`/`wire:model.live` inside an island, so the island partials (grid, list, bulk bar, details panel) call `$wire` from Alpine instead and only the list's page links stay outside the islands; a test allowlists the `wire:` directives in the island markup. Uploads store with `storeUpload(true)` and the queue refreshes the page itself, at most every 2 s. A redirect from the permanent media address to a static URL is cacheable for 5 minutes. Tests: `MediaPartialRenderTest`.
54. **Maintenance page with a reserved permission** (2026-11-12). `/admin/maintenance` runs a fixed list of service commands from the admin (`migrate --force`, one discovered seeder, `optimize:clear`, `optimize`) and keeps a journal of who ran what with the output; the user wanted buttons instead of a console on hosting, a fixed set (no free command input) and super admin only. It is a page of its own, not a settings tab (another permission, no form). `maintenance.run` is the first **reserved** permission (`config/permissions.php` → `reserved`): the `*` of a role's defaults skips it, so the `admin` role never gets it by seeding. Runs happen inside the request (a hosting may have no worker, and a worker keeps old code after a deploy), one at a time, and always in a plain controller request (`POST admin/maintenance/run`, posted by the confirmation dialog), never in a Livewire action: `optimize` boots a second application that resets Livewire's registry of live components, and the cache commands delete the compiled view the component would render from; the lock is the unique `slot` of the journal row, not a cache lock, because clearing the cache wipes cache locks on some stores. Building the config cache (`config:cache`, `optimize`, the page's "Rebuild caches") never applies the stored site settings (`SiteSettings::buildingConfigCache()`, switched by the console's command events), which would otherwise be frozen into `bootstrap/cache/config.php` together with decrypted secrets. Artisan is called only through `App\Support\Maintenance\ArtisanRunner`, which tests replace.
55. **Log viewer on the maintenance page, without a package** (2026-11-14). The Logs tab lists every regular file directly in `storage/logs` (so `single`, `daily` and custom channels need no setting), opens one as it is in a dark viewer with per-line highlighting, and deletes it after a confirmation; the user wanted the raw files, view and delete only, and no dependency (so no entry parsing, filters, search or download). A file is read in 256 KB chunks from its end (`LogReader`), and the viewer fetches them from a plain JSON route (`admin.maintenance.logs.chunk`) into a `wire:ignore` panel, so no request reads a whole file and a log never travels in Livewire's responses. Every read and delete resolves the name through `LogFiles::resolve()`, which accepts only a listed file (no dot files, subfolders or symlinks). Behind `maintenance.run`, because logs can hold personal data.
56. **Content languages are a second set of languages, with the default one unprefixed** (2026-11-14). Interface languages stay as they were (`app.available_locales`, `lang/` folders, chosen per user); content languages are chosen in Site settings → Languages from a built-in catalogue (`config/languages.php`), switched on and off, with one default. They are separate because the catalogue is far larger than the interface will ever be translated into, an administrator must be able to add a content language without a deploy, and every interface language costs a translation of every new string. Addresses: the default language without a prefix, the others under `/<code>/…`; off or not added is 404; the default's own prefix redirects 301 with `no-cache`. Public routes are registered twice with `Route::localized()` and a prefix pattern built from the catalogue (code, not settings), so the routes are cacheable; `SetContentLocale` decides per request and is a Livewire persistent middleware. `/login`, `/settings/*` and `/admin` carry no prefix; a guest sees them in the language of the site they last visited (session) when the interface has it. The site's default interface language is read from `content.interface_default`, never from `app.locale`, which holds the request's language. The user asked for the foundation only: no content models, no theme strings yet.

## Conventions

- **Translations:** PHP files only in `lang/en` and `lang/uk`. Keys are snake_case and nested by page/block. Every new key goes into both languages in the same change. `tests/Feature/Localization/TranslationParityTest.php` checks file/key parity, empty values and placeholders, that every `__('group.key')` used in `app/` and `resources/views/` exists, and that every vendor-map target exists.
- **Languages:** interface languages are `config('app.available_locales')`; the `SetLocale` middleware (web group) applies `users.locale`, else the last visited site language, else the site's default (`ContentLocales::interfaceDefault()`, not `config('app.locale')`). Content languages are `App\Support\Localization\ContentLocales`; public routes go inside `Route::localized()` and build their addresses with `ContentLocales::route()`.
- **Permissions:** declared in `config/permissions.php` (`groups`) or by modules via `PermissionRegistry::register()`. Run `php artisan permissions:sync` (`--prune` deletes stale ones). Labels go in `lang/*/permissions.php`; a test checks that every permission has a translation. Code checks permissions (`can('users.edit')`), never role names; the only exception is super-admin in `Gate::before`.
- **Admin routes:** `routes/admin.php`, prefix `admin`, names `admin.*`, middleware `auth, verified, can:admin.access`.
- **Tests:** `seedRolesAndPermissions()` (tests/Pest.php), and the factory states `User::factory()->withRole('editor')` and `->withPermissions([...])`.
